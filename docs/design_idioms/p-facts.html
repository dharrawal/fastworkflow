What a phase hands on

A planning command is a command whose work is a plan of steps instead of a body (A plan in place of a body). Each public method of its class PlanGenerator is a phase: it returns a list of steps, such as run("find_book", query=...), and the phases run in the order written (A step the code runs). Often a later phase, or __result__ (the method that writes the answer, The answer, in code), needs what an earlier phase found, such as the uids a search returned. What a phase hands on is called its facts. Reach for this shape whenever later code must read a command's result as typed fields.

You declare the facts with the phase method's return annotation, the -> X after its parameters. After the phase's steps have run, the framework builds the facts from those runs, with no model call, and passes them to any later method that has a parameter with the same name as the phase. There are three forms. In each, X.Output is the Pydantic model command X returns, reached through its Signature, imported from its file in the same _commands folder.

A phase with no return annotation hands nothing on: a later parameter named after it receives None. That suits a phase whose steps only act, such as a move.

One command's Output

The parameter find below gets the facts of the phase find, and reads find.book_uids like any Pydantic model. When a phase was skipped because it returned no steps (A phase that does not run), the parameter is None.

The facts come from runs of this phase that succeeded, on the one record the phase worked on, and that do one of its planned steps. A run on another record never counts, so a facts model cannot hold runs on two records. A few runs stand in for a planned step: a lookup done in another form whose output holds the step's values counts, and a lookup that listed nothing beside one that listed rows does not. An earlier phase's runs count in one case only: the run that entered the record the phase's opening step would open. run-code sees only the phase's own runs, so that case applies only in a real run. When a required field finds no run, the phase fails with "no successful run of 'X' fills ...", which does not say that a run on another record was set aside. When the command ran more than once in the phase, the latest run is used, except that runs differing only in paging use the first page's run. A step written with all_pages=True joins every page into one Output (Every page of a list).

Whichever command ran

When a phase runs one command or another, depending on the request, annotate it with a union of their Output classes. Example: "is there a member named Lee?" runs find_member, "do you have a book called Emma?" runs find_book. The input field that chooses is usually a Literal, so the request can only name one of the choices.

The framework looks at the phase's successful runs, newest first, and takes the first one whose command is a member of the union. If the phase ran none of them, the phase fails and the call stops. fastworkflow command preview lists the output as "Library/find_book's Output | Library/find_member's Output", with one facts table per member, so the agent planning the call sees both shapes. Read a field only one member has (find.names) only after checking which ran, as the example does by branching on input.kind; otherwise __result__ fails with 'Output' object has no attribute 'names'. The saved facts record which member filled them (an internal key that no stop entry, answer text or span shows), so a later phase, __result__ and a restored session all get the member that ran, whatever the members' field names are.

Several commands: a facts model

When one phase runs two or more commands and later code needs what each returned, write a facts model: an ordinary Pydantic model with one field per command, each typed with that command's Output. Annotate the phase with it. The framework fills each field from that command's successful run in the phase.

Run on the book Dune, shelf.book.title is the title show_book returned, and the answer reads "Dune is held at Central, 3 copies, 1 free; on loan to 2 borrowers (Ann Lee, Raj Patel)." A field may be only one of three things:

  • X.Output: required. A phase with no successful run of X fails.
  • X.Output | None = None: None when the phase ran no X. A default of None alone, or | None alone, makes the field optional too.
  • X.Input: the arguments X was called with.

A value you compute yourself, such as the count of free copies, is a property or a method of the model. The model may have validators; one that refuses fails the phase. A field of any other type fails the load of the command (see what a mistake stops): "Shelf.title is str; a facts field is typed with a command's Output or Input. Compute other values in a property or method of Shelf". A field cannot be a union of two Outputs either (the same message, which does not say which commands); when one of several commands runs, put the union on the phase, as above.

What else the annotation can be

A union is read in two places on this page: on the phase (A.Output | B.Output, whichever ran) and on a facts-model field (X.Output | None = None, optional). Here Optional[X] and X | None mean the same. Do not write -> X.Output | None on a phase: it fails the command's load ("its return annotation ... includes None; ... leave '| None' out"). A later phase reads the facts of a phase that did not run as None through a parameter whose default is None.

  • When the facts type depends on the call's input, @phase(output=lambda input: ...) takes the place of the annotation. output= takes a function of input alone; a fixed facts type is the return annotation. Writing both is a load error.
  • On a phase marked @phase(over=...), the annotation is one item's facts, and the later parameter receives a list of them (Once per item).
  • Do not annotate a phase with a command's Input alone (-> FindBook.Input). It is a load error now: a phase hands on a command's Output, a union of Outputs, or a facts model, and the command that wrote it does not load. To keep the values a command was called with, use FindBook.Input as a field of a facts model.

Mistakes a beginner makes

  • Annotating a phase with what the method returns, its list of steps (-> list[str]). The command does not load (the rest of the workflow does): phase 'find': its return annotation must be the facts model it fills (a pydantic model), got list[str]; a model that depends on the input goes in @phase(output=lambda input: ...). The annotation names the facts, never the steps.
  • Annotating a command the phase's steps never run. The command does not load: phase 'find' hands on find_book's Output, but none of its steps runs find_book. For a union the check is made for each plan the inputs give, so every choice must run at least one member. If it runs anyway, the phase finds no run to fill its facts and the call stops: no later phase runs, and the answer is the facts found so far plus a line naming the phase that failed.
  • A union member that is not a command's Output, such as your own model Other: "phase output Other is not a loaded command's Signature.Output". The command does not load.
  • Reading a field the Output does not have, such as find.book_count. The next phase fails with 'Output' object has no attribute 'book_count' and the call stops. Read the field names in the other command's class Output.
