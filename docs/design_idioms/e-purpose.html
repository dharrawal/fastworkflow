How a request finds your command

A user types a sentence, and the framework has to decide which of your commands it means. This step is called intent detection. You help it with two things you write on the Signature class of every command file: its docstring, one sentence saying what the command does, and its seed utterances, a list of example requests named plain_utterances. Write both for every command a user can ask for in words.

A command here is one Python file under _commands/: an execution command runs your code once, a planning command (see a plan in place of a body) runs several steps. Both read the docstring and the seeds the same way, with one difference at load: a planning command with no docstring does not load (Signature needs a docstring (the planning command's description)), while an execution command without one loads and is described by its name in words in training and to the remote model, and by its bare qualified name, with no description, in the which-command question. A command file that fails to load fails that command only: fastworkflow run_cli, fastworkflow train and the server list it before they start, train stops, and command preview --check fails (see what a mistake stops). How a confident match is acted on also differs; see "Who reads them" below.

The purpose sentence

A good docstring:

  • starts with the verb a user would use (Show, Count, Open, Say who) and names what it acts on and what comes back;
  • tells this command apart from its neighbours, because the which-command question below puts them side by side;
  • keeps a condition or a limit for a second sentence (One member per call.), so the first sentence, the one training uses, is only the purpose;
  • fits on one line.

Training reads only the first sentence, which ends at the first ., ! or ? followed by a space (and only in the default embedding layout: the two fine-tuned layouts read no docstring). Every other reader is shown the whole docstring, joined onto one line. A Context docstring is cut at its first line instead, which is a different rule. So the first sentence has to stand on its own, and anything after it is read too.

Seed utterances

Aim for about eight seeds, and vary the kind of sentence: an order, a question, a short casual line, one with a value in it and one without. Use the values a real user would type, such as a uid or a title. Put the most typical requests first, because the remote model (below) sees only the first nine; fastworkflow command preview --check prints a notice for a command with more. The rest still train the local model. A command needs no Input to be trained: the library's show_book has none.

Who reads them

  • The command's name. Before any model, a request whose first word is a command's exact name runs that command. A request that is, as a whole, a misspelling of one name (add_notte for add_note; case, spaces and underscores ignored) is taken as that command, but it is not the user naming it: a command that changes data or carries an approval mark found that way is confirmed first. A request that only begins like a name (a, show me) is not a misspelling; it goes to the models below.
  • Training. fastworkflow train first has a language model (the one named by LLM_SYNDATA_GEN) write new requests in the style of your seeds, as a few different kinds of people would ask them; they are cached and written again when the seed list changes, and also when the command's name, the persona or utterance counts, the generating model or the prompt-building code change. The training rows for the command are then its name in words (open book), your seeds, the generated requests, and the first sentence of the docstring. Each seed counts three times as much as a generated request, because you wrote it. The local intent model, a small classifier stored in the workflow folder, is fitted on those rows in seconds. At run time the local model matches a message that reads like your seeds to the command, with no model call. That match runs at once only for an execution command that does not change data: a confident match to a planning command is confirmed by the remote model, or asked about when JEV_API_KEY is not set, and a match to a command that changes data or carries an approval mark waits for the user's yes (see a command that changes data).
  • The remote intent model. When the local model is not sure and JEV_API_KEY is set, a remote model is asked. It sees each candidate as - name: docstring followed by its first nine seeds. A command that only enters another context (it declares @descends_to and takes no required input) is never among the candidates: its exact name and the local model still reach it.
  • The which-command question. When more than one command still fits, the user (or the agent) gets a numbered list, one line per command: its name and its docstring. When exactly one fits, the "/" path asks "Did you mean the command 'X'?" instead, and the plan path takes it and lets the turn's review confirm it.
  • The planner and the agent. Their listing of the commands they may call puts the docstring on the line under each name, always.
  • "what can I do". The built-in what_can_i_do command prints the docstring. In agent mode, in a workflow with planning commands, a message that only asks what the assistant can do is answered in code instead: each planning command in plain words with its shortest seed as the example, then the other commands by name, with no docstring.
  • Planning commands only. The request splitter, which cuts a message that asks for several things into parts, is shown one line per planning command, its name and its docstring, as the kinds of job a message may hold (see splitting a request). fastworkflow command preview opens each preview with the docstring, and the chat page shows it on its plan buttons.

What train checks

  • These three checks cover execution commands only; a planning command is trained like one but is skipped by all three, so a planning command with two seeds gets no guidance and a planning command's seed that is a benchmark request does not stop the run. For an execution command with fewer than eight seeds there is a yellow "Seed guidance" line. It is advice; training goes on.
  • Two execution commands whose seeds look alike are printed as a pair. Make the seeds tell them apart, merge the commands, or record the pair as intended in accepted_duplicates.json in the workflow folder.
  • If the workflow has an intent_benchmark.json (the requests used to score routing), a seed that is also a benchmark request, ignoring case and end punctuation, stops the run with an error. A score on requests the model trained on only measures memory.

Beginner mistakes

  • Writing the description in the module docstring (the one at the top of the file), or the seeds at the top of the file or on ResponseGenerator, instead of on class Signature. Intent detection and every listing read both only from Signature (only the README that fastworkflow build writes shows a module docstring): what is written elsewhere is ignored, so a command with neither trains on its name alone, and a planning command with no docstring there fails to load.
  • An abbreviation such as e.g. or i.e. in the first sentence: the sentence is cut there, so training learns half of it.
  • Pasting a benchmark request the model got wrong into the seeds: train stops, as above. Write a new sentence with the same meaning instead.

Older command files, such as those in hello_world and retail_workflow, also define template_utterances = [] and a generate_utterances method. The framework does what that method does when it is absent, which is to train on the command's name and the seeds; a body that differs (14 of the 15 retail files) is still honoured, and in the two fine-tuned layouts can leave the name-in-words row out (the default embedding layout adds that row anyway). template_utterances trains nothing, though the duplicate scan and the seed hash read it. A new command writes only plain_utterances.

See also the shapes the framework reads, for the other docstrings it reads (on class Context, on Input and Output models) and the ones it ignores.
