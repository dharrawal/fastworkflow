01

One file, two classes

A command is one thing a user can ask your workflow to do, such as "when are you open?". Each command is one Python file in your workflow's _commands/ folder, and the file name is the command's name.

Put the file directly in _commands/ when the command needs no object to act on: it can then be found from everywhere (see commands with no object). Put it in a subfolder, such as _commands/Book/, when it acts on one kind of object: the folder name is that kind, called a context (see a folder for one kind of object). Files whose names start with _ are not commands.

The file holds two classes. The framework finds them by name, so spell them exactly: a file that has a Signature but no class named ResponseGenerator (or PlanGenerator) is reported when the workflow loads, and its command is unavailable.

  • Signature describes the command. Its docstring says what the command does, and the framework uses it to pick this command for a request (see the purpose sentence). plain_utterances are example requests the intent model (the classifier that picks a command for a message) is trained on (see seed utterances). The optional Input lists the values the command needs; the framework reads them out of the user's words and asks for any that are missing (see an input). The optional Output is the typed result; a command that declares none returns a text (see what it returns). Nothing else public goes on Signature: its members are Input, Output, plain_utterances, generate_utterances, template_utterances and, on a planning command, template (planning_commands.SIGNATURE_MEMBERS); any other fails the command's load, and a helper's name starts with _. A declaration decorator (@writes, @user_approval_for_execution, @descends_to) put on Signature fails it too: declarations go on the generator class. So does an Input field whose default is the framework's not-given marker (default="NOT_FOUND"): a required field has no default, and an optional one is <type> | None = None (see an input).
  • ResponseGenerator does the work. Its __call__ runs your code.

__call__ takes exactly three arguments after self: the workflow, the user's message as text, and the filled Input. For a command with no Input the third argument is None. The workflow gives you the object the command acts on, workflow.record (see the record it acts on). Return the Output and the framework sends it as the response to the user or to the agent (the language model that calls commands for the user in agent mode, the default) (see what it returns). To say no, raise fastworkflow.Refused with a message; the user sees that message.

The common mistake is a __call__ with two arguments, (self, workflow, input), or with a default such as input=None. The command does not load, and fastworkflow run, train and the server list it before they start: ResponseGenerator.__call__ must take three arguments ... it takes 2 here, or, for the default, input has a default here, which it must not have. A second mistake is to read the second argument as the command's name. It is the text the user typed only when a user's message reached the command; for a step of a plan it is the generated step text, such as find_book query=Dune, for a startup action it is an empty string, and for a direct call from a client it is whatever the client sent.

A command that runs a plan of other commands writes a PlanGenerator in place of the ResponseGenerator (see a plan in place of a body). One file cannot hold both: like every other mistake on this page, it fails the load of that command only, and the rest of the workflow loads (see what a mistake stops). A file with a ResponseGenerator and no Signature is still a command; the startup command is one (see the root object). Two more mistakes fail that command's load the same way: a file in _commands/ with neither a Signature nor a generator (a helper you forgot to start with _; the message says to name it with a leading underscore), and a generator that is imported or assigned rather than defined: a generator is a class defined in the command's own file (it may inherit a base from a _ helper module). An async def __call__ fails the load too: the framework calls it synchronously.
