Field options

A field option is a key you put in a field's json_schema_extra dict to turn on one extra behaviour, such as "strip the word 'the'" or "let a classifier decide this yes/no value". Two declarations change no behaviour at all: they are training data (see training data only). Reach for one only when a field's value is not simply a word or number the user typed. Most fields need no option at all.

A few terms first. An input is a field of your command's Signature.Input pydantic model (see an input). An execution command runs your Python code; a planning command runs a plan of other commands (see a plan in place of a body). The command text is what the user typed for the command, plus their replies to its questions. The options work the same on both kinds of command unless the table says otherwise.

Why most fields need nothing. By default the value the model fills for a str or int is used as it is: it is not compared with the command text, because the model may convert it (a date from "tomorrow"). A few checks that need no option still run on every field: a value that is entirely a template token ({name}, <name>; an id such as SKU_42 and a JSON string such as {"a": 1} are values), pronouns and workflow vocabulary words, and, on a field you did not mark, the remote "was this value given" check, which skips any value the request writes at word boundaries (the paragraph "Checks that always run" on an input lists them). copied_from_command_text is the explicit strict check that makes the value be one the user wrote (taught on an input). The other options add behaviours the default does not have.

Every option at a glance

Most keys take True or a small dict of their own options; from_command_output takes a text or a list of texts, and examples_by a dict of dicts of lists (below). Leave the key out to turn it off: False fails the load. "Load" means the moment fastworkflow run_cli, fastworkflow train or the server reads your command files; a command that fails to load is reported there and does not run.

Two keys that clash also fail the load: copied_from_command_text with record_named_in_command_text, and the two classifier keys together. Every key that is not an option fails the load, on either kind of command, and the message names the key, the closest option when one is close ("copied_from_command_txt" gives "did you mean 'copied_from_command_text'?") and the valid keys. A planning command's Input field holds its options only. An execution command's Input field also takes the JSON Schema annotations (examples, description and the like), because its parameter-example generator reads description and examples there; write them as Field(examples=...) all the same, where both kinds read them. An Output field of either kind takes only ui and the JSON Schema annotations (examples and the like). Never write available_from (the framework writes it from from_command_output) or a retired spelling such as in_request or verify; a retired spelling fails the load with a message naming the key that replaced it (see removed). A planning command's Input also limits its field types, because its values arrive as text: str, bool, int, float, list[str] or a Literal of text, Optional only as Optional[str] = None, and default_factory only list on a list[str]; any other type fails the load and the command is skipped. An Optional[int] fails with a message that says an argument the request leaves out is empty text, which a number cannot be; write start: int = 0 or Optional[str] = None. The same field-type rule is applied to an execution field that carries a check option, with one difference: a marked Optional[int] = None (or int | None) is accepted on an execution command, where an absent value is simply not checked. Five names are reserved on a planning command's Input for the framework's own planner inputs and fail the load: user_query, available_commands, steps_before, steps_after and reasoning.

The request's own words

Two options say the value must come from the command text.

  • copied_from_command_text with ignore: the listed words are removed from either end before the check, so "the Riverside branch" gives Riverside (the first figure). Its list[str] form checks each item; without it, list items are not checked.
  • record_named_in_command_text: the value must also be the name of a record (a person, a group, a code) that the command text names, not a stray word such as "I". It takes the same ignore list.

"copied_from_command_text": True on a str or int is the strict check, and what it does is exactly this. A str must be written in the command text as whole words (its first and last characters do not continue into a letter or digit of the text, so "Ann" is not written in "Joanna"; case is ignored and any kind of dash counts as a plain dash) and takes the command text's spelling; an int must be a number the command text writes, and is refused when the text writes none. This holds for a required and an optional field alike (a marked value the model did not give is not checked), and it is one check, the same function on both kinds of command. Two marked fields may hold one value only when the user's request writes it as often ("New York, New York"); otherwise a field gives the value up (the first whose name, as words with an optional plural s, is not among the four words before the value in the request, an optional one first): an optional one is left empty with a line that says so (on the review, on any question, and on the trace), and when both are required one is refused and asked again. A field with no option is not compared with the command text, nor with another field, and a pydantic pattern neither adds the check nor removes it: it only validates (and the model is told the format). The model reads sentences after your description, from your declarations only and the same on both kinds of command: "Copy it exactly as the request writes it." on a marked str, "A number the request writes." on a marked int, a sentence for a marked list[str] or record_named_in_command_text field, "True only when the request asks for it." on every bool ("False only when the request asks against it." when it defaults to true), and the pattern of a field that declares one. An unmarked str is told nothing about copying, on either kind. And when the workflow declares id formats, a part of an id the model copied is widened to the whole id, on a marked field only (see identifier formats). So write the description for a person, and leave instructions to the model out of it.

These checks only ask "is this written?". For any other rule about the user's words, write a validator: it reads the same command text as info.context["command_text"] (see correct or refuse).

A value a classifier decides

Some values are not words you can copy. "Show me Dune, and who has it" asks for loans, but no word in it is True. A yes/no input, or a choice between a few fixed values, is easy for the filling model to get wrong. The classifier options ask a second, separate model (a classifier) to decide the value from the request alone (the second figure).

  • classifier_confirms: the model fills the field as usual, then the classifier decides it again. When the classifier is sure (a probability of at least 0.65), its answer replaces the model's; otherwise the model's value stands. The {"meanings": {value: text}} form, on a Literal, shows the classifier each value with its meaning, and the chat page's question form labels each choice with it ("value — meaning"); every key must be one of the Literal's values. On a str with record_named_in_command_text, the classifier picks which of the records the request names is meant, or "none".
  • classifier_decides, on a bool: the model never fills it, and any value given for it is ignored. A sure classifier answer sets it; otherwise it keeps its default.

The classifier reads the request and the field's description (and the meanings). So write the description as the condition for the value, such as "the request asks who has the book on loan".

The classifier is the remote decision model, Jev, and needs JEV_API_KEY. Without the key no check runs: a classifier_confirms field keeps the model's value and a classifier_decides field always keeps its default. Nothing fails; the startup log has one INFO line naming the fields whose checks are inactive. When the classifier disagrees, the user sees nothing: no question, no message. The command runs with the classifier's value, and the turn's trace records a note such as loans=False -> True (check 0.90).

Training data only

Two declarations tell the synthetic utterance generator how users talk about a value. No check, extraction, planner or client reads them, and in this tree no generator reads them yet either (the generator is planned work, not shipped). They are still checked at load, so a mistake fails the load and names the field and the rule. Like any edit of a command file, editing them retrains that command.

  • "classifier_confirms": {"words": {value: [word, ...]}}, on a Literal: the words or short phrases users write for each value, such as {"group": ["team"]}. Every key is one of the Literal's values, every list is non-empty, a word is listed once per value (case ignored) and under one value only; a value may have no words. It sits inside classifier_confirms, so it turns the classifier check on: {"words": ...} with no meanings is the same check as True.
  • "examples_by": {choice field: {choice value: [example, ...]}}, on the field whose example values depend on a choice: it names exactly one other field of the same Input whose type is a Literal (or Optional of one), each inner key is one of its values, and each list is non-empty and holds values valid for this field (its type, pattern and bounds, checked strictly, so "5" is not an int; None is never an example). A choice value may have no entry.

Beginner mistakes

  • Marking copied_from_command_text on a value the model has to compute, such as a date. Every correct answer is refused as "is not written in the request", and the user is asked for a value they already gave. Leave a computed value unmarked.
  • Leaving a name, a title or an id the user must write unmarked. The model's value is then used even when the user never wrote it. The argument_check_not_in_request attribute on the extraction span names such fields.
  • Relying on classifier_decides on a machine without JEV_API_KEY. The field is then always its default, whatever the user asks, with no error. Use classifier_confirms if the model's guess is better than the default.
  • An option on a type it does not fit, such as copied_from_command_text on a bool or meanings on a bool. The command fails to load, and the error names the option, the field and its type.
