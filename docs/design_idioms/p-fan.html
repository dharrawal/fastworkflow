06

Once per item

Use this when a request needs the same small job done for each thing an earlier step found: "open each book by this author and tell me its copies". You write the job once, for one item, and mark the method with @phase(over=...). The framework runs it once per item and hands you the results as a list.

A few words first. A planning command is a command whose file lists steps for the framework to carry out instead of running its own code (see A plan in place of a body). Its PlanGenerator class splits the job into phases: each public method is one phase, run in the order written, and returns its steps as a list. A phase's return annotation is the facts it hands on, the typed Output of a command it runs (see What a phase hands on). A later method reads them through a parameter with the phase's name.

What each part does:

  • over="find.book_uids" names the list: the phase find, then a field (or property) of its facts. Every name of the path is checked when the workflow loads, except the names after a property with no return annotation (-> list[str]), which are checked when the phase runs. A path that ends on one value rather than a list fails the load ("reads one value ..., not a list, so the fan-out would run once"). Empty values and repeats are dropped, order is kept. over may also be a list, or a function of input that returns one.
  • The method's one parameter that is neither input nor the name of a phase receives the item, here uid. A parameter named after a later phase is excluded too, and a parameter with a default counts as a second item. With no such parameter, or with two, the command fails to load, naming the phase (the load reports plan() fails on placeholder inputs).
  • max_items caps the items run (10 when you leave it out). When the list was longer, the answer ends with "Note: only the first 5 of 7 books were covered." noun is the word that note uses, "items" without it. until=, a function whose parameter named after the phase gets the items' facts so far, stops the fan-out when it returns true; a phase with until writes no cap note. max_items, bind and until on a phase with no over= fail the load ("is for a fan-out phase, which runs once per item: add over=..., or leave ... out"), and so does noun.
  • bind (default True) says each item is a record its steps open, like the book open_book opens. Write bind=False when the items are not records, for example names or uids you only look up. A bind that is not True or False (or a function of input) fails the load.
  • Like over, every other option (max_items, noun, bind, optional, until) may be a function of input alone, decided when the call is planned.
  • Any parameter named after the phase (in __result__, as here, or in a later phase) gets the LIST of the items' facts, typed, in item order. It is empty when the list was empty; the phase then runs nothing.

At run time each item is its own small run: the framework writes that item's steps by calling book(uid), and code runs the steps it can (see A step the code runs) before a model takes any step. Each item gets a fresh budget of 15 model steps (when the fan-out is the command's only phase, each item gets the agent's own step cap instead). The count of writes resets too: a command marked @writes (see A command that changes data) that an item's steps name once may run once for each item, never twice for one. Nothing moves the workflow back between items, so the second item starts where the first ended; a step whose command belongs to an enclosing context, such as open_book on the library, still runs there. Inside a planning command that another planning command called, the turn-wide limit FW_TURN_MAX_STEPS (default 400) also stops the remaining items once it is spent.

When one item's step is left open (code cannot write it in full), the agent's model does the rest of that item's steps, and the next item starts again with code. With no agent model configured (LLM_AGENT unset), the command stops at that step instead, and the answer says what ran; a yes-or-no step, or a step missing one plain value, asks the user first when someone is there to answer. When an item cannot be filled, the whole command stops: later items and phases do not run, and the answer shows the facts gathered so far and a line that starts "This job stopped at its part 'book', which failed: item b3: ..." naming the phase and the item. Mark the phase @phase(over=..., optional=True) when the answer can do without it: a failed item then makes the phase count as not run (the items that did succeed are dropped too, and __result__ gets None for it), and the next phase runs.

The beginner's mistake: keeping bind=True over items whose steps never open a record. When the phase has a return annotation (facts), each item then fails with "item b3 was never opened: no command ran on a record that names it"; with no annotation the item does not fail, and the agent's run is only told to open the record. fastworkflow command run-code <workflow folder> author_books --input '{"author": "Jane Austen"}' prints one "Phase book (item b3)" block per item; each item's open_book, a Library command, runs on the library although the workflow stands on the previous book, as in a real run. run-code does not check bind (it fills an item that was never opened, which a real run fails), does not evaluate until, prints no cap note, and exits 1 on a failed item where optional=True would drop the phase.
