01

A folder for one kind of object

A context is one kind of object in your application, such as a book or a member, together with the commands that act on that kind of object. In a workflow it is a folder under _commands/ named exactly after the Python class of the object.

Reach for a context folder when a command only makes sense on one particular object: "show this book" needs a book to show. The folder groups those commands, and the framework offers them only while the workflow stands on an object of that class.

"Stands on" means: the workflow always holds one current object, workflow.record (the record). The framework takes its class name (Book), offers the commands in _commands/Book/, and inside each of them workflow.record is the book.

What the framework reads in a context folder:

  • Each .py file is one command of the context, execution and planning commands alike (one file, two classes); a folder that holds only planning commands is a context too. Its name is the file name, qualified by the folder: Book/show_book.py is the command Book/show_book.
  • _Book.py, the file named after the folder with a leading underscore, holds the context class, always called Context. It is optional, and it describes the object rather than adding commands (below).
  • Any other file whose name starts with _ stops the workflow when it loads. Helpers that several commands import live in the workflow's helper package, _commands/_shared/ (see helper modules).

The object the workflow starts on, built by the startup command (see the root object), is a context too: its commands live in a folder named after its class, here _commands/Library/. A command that moves the workflow onto a book (see move onto a record) is what makes the Book folder's commands available.

Commands with no object

Some commands are not about any one record. "When is the library open?" means the same thing whether the user is looking at a book, a member or nothing at all. Put such a command's file directly in _commands/. It is then a global command, and the user can reach it from anywhere in the workflow. These files form the global scope, which the framework names * and shows to a user as "global". The file is an ordinary command file named just library_hours; where it sits is all that makes it global.

Which record it runs on. When a request finds it (typed by name or in plain words), a global command runs on the root object: inside it, workflow.record is the library, wherever the user stood. Running it does not move the user; after the hours are shown they are still on the same book. A direct action sent by a client (an MCP tool call or a direct HTTP action) and a step of fastworkflow command run-code run it on the root too.

When a request reaches it. The framework searches a lookup path, the scopes it may use from where the user stands, nearest first; standing on a book that is Book, its base Record, then Library, then the global scope (the enclosing record explains the climb). A message that starts with a command's name (library_hours Central) is matched with no model call; the nearest scope with that name wins. For plain words, such as "when are you open?", the trained intent model is asked. In a trained workflow whose root object is set, the global scope is asked first: a confident answer there runs; otherwise the scopes where the user stands are asked, nearest first. With no trained global model, the global scope is asked last.

The context class

The optional _<Folder>.py file holds one class, class Context, where you tell the framework facts about that kind of object. Every part of it is optional except get_parent and parents, in a workflow with a root, on a context whose records are not the root:

  • Its docstring. The first line describes the context in the list of other contexts the agent sees, and replaces the list of that context's commands the line shows when there is no docstring. Only the text up to the first line break is shown.
  • inherits = [...] names the contexts whose commands this context also has: commands shared through a base.
  • parents = [...] names every context a record of this context can sit in, and goes with get_parent: one without the other stops the workflow. Both declarations are lists of context names written as string literals in the class body, read without importing the file.
  • get_parent names the enclosing object, so the outer object's commands stay reachable: the enclosing record. The root object's class has no enclosing object and needs no get_parent. In a workflow with a root, every other context needs it: with no _<Folder>.py or no get_parent, the first climb from such a record raises MissingGetParentError, naming the context, the file and the method. In a workflow with no root it is optional, and leaving it out means the same as return None: the climb goes straight to the global commands.
  • get_displayname and instance_label_attr, the record's name and identity (next).
  • state_version, get_state and from_state save and rebuild the object when a session is put away, and get_locator and find_by_locator find a record inside it: remember the object.

Every fact about a context is declared here, in its own file; fastworkflow command preview draws them all together as the workflow's object model (see the enclosing record).

A record's name and identity

Write these when people or the agent need to know which book the workflow is on, not only that it is on a book. The framework never derives one from the other, and never guesses either.

At the root record the agent's line names no record, because every turn starts there. A command that ran on an enclosing record is filed under that record and its identity. An identity that must be computed is a property on your record class (see the shapes); the printed value has parentheses, semicolons and line breaks removed and is cut at 80 characters. Saving a session reads neither line.

Mistakes

  • A folder name that differs from the class name. The match is exact and case-sensitive, and it is on the record's own class name: a folder Books/ for the class Book is never chosen, and a record of a subclass such as RareBook gets no context either. The load does not catch it, even when the moving command declares @descends_to("Books"). The move does: a command that moves the workflow onto such a record fails with "... Book is no context of the workflow: a context is the folder _commands/Book/, named exactly as the record's class", and the record is put back.
  • A context file whose class is not named Context. A _Book.py that defines class BookContext is reported when the workflow loads ("is the context class file of Book but defines no class Context"); rename the class.
  • A folder with no command file. Every context is a folder. A folder holding only _Paperback.py is a context whose commands are all inherited: it loads when its class Context declares inherits naming a context that has commands (see commands shared through a base), and its _Paperback.py is read. A folder that holds no command file and inherits none stops the workflow ("the context folder 'Paperback' holds no command file and inherits none"). Only files directly in the folder count; a subfolder is not read. A folder whose name starts with _ is skipped whole, and a folder named Core is dropped from the contexts, both without a message.
  • A global command that needs the user's record, such as "renew this book": it gets the library as workflow.record. Put it in the context's folder. And give a global command a name no context command has: typed inside that context, the name runs the context's command, while plain words go to the global one when the global model is confident. The same global-first rule can take a plain-words request away from a context command on the user's record.
  • instance_label_attr naming a plain method prints "<bound method ...>"; make it a @property. An instance_label_attr naming an attribute the record lacks, or one that is not a string, gives an empty identity with no message; a misspelt instance_label_attr itself (such as instance_label_atr) is a public member that is no hook, and stops the workflow. A classmethod called instance_label on the context class is a removed spelling: the workflow does not load, and the error says to use a property named by instance_label_attr.
  • A misspelt hook, such as get_displayName: every public member of class Context must be a hook, so the workflow does not load, and the message lists the hooks and says a helper's name starts with _.
  • A docstring wrapped mid-sentence. The agent reads only its first line, so it gets half a sentence.
