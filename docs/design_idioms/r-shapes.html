Plain Python, read by the framework

Everything you write in a fastWorkflow app is ordinary Python: classes, docstrings, Pydantic fields, type annotations, unions, properties and subclasses. A few of them, in a few places, are also read by the framework and change what it does. This page is the lookup table of those places, grouped by the Python construct. Come here when you meet one of them in a command file and want to know whether the framework reads it, and which page teaches it. The last group lists the names the framework looks for, because a name is read too. The table lists the places known to be read; it is not proven complete. Three name rules are known and on no other page: an Input field named query gets no "Identify the query" step in the extraction prompt; a facts model with a str field uid and a str field label is printed as one line, "Dune (uid b1)", in the facts a stopped call shows, where a ..._uid list beside a text list of the same length is left out; and in that text a field named labels, ..._label or ..._labels is printed as an English plural (permission_labels as "permissions", labels as "names").

Two words used below. A command file is one Python file in _commands/ that defines one command (see one file, two classes). A planning command is a command whose body is a plan of other commands, split into phases (each public method of its PlanGenerator); what a phase hands on to later phases is its facts (see a plan in place of a body).

The docstring on an Input or Output model

Pydantic turns a model class's docstring into the description of its JSON Schema. The server publishes those schemas: GET /command_schemas lists each command's Input and Output schema, and in the example MCP server (fastworkflow/mcp_server.py) a command with an Output gives its schema to its MCP tool as the tool's outputSchema. So a client or an agent reading the schema sees your docstring. When a planning command's phase hands on that Output as its facts, fastworkflow command preview prints the docstring above the facts table. The docstring is optional, and no model call reads it: the parameter extractor reads each field's Field(description=...) instead. The same holds for any Pydantic model a phase returns.

Docstrings the framework does not read

The module docstring at the top of a command file; ResponseGenerator and its __call__; PlanGenerator, its phase methods and __result__; your helper functions; and a string written under a field. Write them freely for your colleagues: changing them changes nothing at run time. Two of these catch beginners. A command described in the module docstring instead of in class Signature is described only by its name, and a planning command then fails to load with Signature needs a docstring (the planning command's description). A field described by a string under it is ignored by Pydantic, so the extractor knows only the field's name: use Field(description=...). And keep a Context docstring's description on its first line, since only that line is shown.

Two mistakes with class names, both load problems

  • A misspelled ResponseGenerator, such as class Responder. A file with a Signature and neither class is a load problem: "has a Signature but no ResponseGenerator or PlanGenerator; the class name must be exactly ...". That command is unavailable and the rest of the workflow loads. A file with a generator and no Signature (a startup command) is not reported; a file with neither fails the load, saying to name a helper module with a leading underscore.
  • A context class not named Context, such as class BookContext. The file _Book.py is a load problem: "is the context class file of Book but defines no class Context". A folder with no _Book.py at all is still fine.
