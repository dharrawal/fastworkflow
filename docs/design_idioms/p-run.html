A step the code runs

A planning command does its work as a list of steps instead of a Python body (see a plan in place of a body). Each method of its PlanGenerator class is a phase, and returns that phase's steps. A step is either run("command", ...), which the framework runs itself, or a plain sentence, which a model carries out. (A plain string that is written exactly like a command step, a command name and key=value pairs, is also run by code, as run() would; only fastworkflow command preview warns about writing it by hand, so write run().) Reach for run() whenever a step is simply "call this command with these values": code runs it in order, with no model call. Two keyword options cover what a plain call cannot: opening a row by the name a search found (named=) and reading every page of a long list (all_pages=True).

run("find_member", query=input.member) names an execution command (a command with Python code behind it, see one file, two classes) and passes values by the names of that command's own Input fields. A value of None is left out of the step. run() writes the step as text, and every reader of that text (the step parser, the code that runs it, the preview and the template) must read the same value back, so a value that has whitespace, a quote, a separator character or a condition word (such as "only", "when" or "if") is written in quotes: find_book query="When Harry Met Sally". Multi-word values therefore show quoted in previews, in run-code output and in the commands an agent sends. A value that holds both kinds of quote stays unquoted, which is a known limit. A placeholder such as <input.title> is not quoted.

Code runs a phase's steps one by one, through the agent's own command tool. It runs a run() step when every required Input field has a value, when it is a named= step whose row code can find (below), or when it leaves out exactly one required uid or from_command_output field (see a handle's producer) and the command run just before it in this call listed exactly one row with no further page: code takes the value from that only row. If the command lives in another context (a part of the app, such as one open book), code first moves there when that needs no value. A command that exists in several contexts whose Input classes would give different steps is an open step. A sentence that begins with an answer word such as "say" or "report" is about the answer, so code passes over it. Code also passes over a step that opens with such a word and then names a command ("report the result of find_member query=x"), a step in which a negation word (not, no, never, none, without, skip and a few more) comes before the command's name, even inside a condition ("if the member has no fines, list_loans"), and a step that names only a built-in navigation command such as go_up. A run() step writes its command's name first, so the first two do not apply to it.

Where code stops: the open step

The first step code cannot run is the open step: a sentence that asks for work ("choose the book the request means"), a run() step still missing a value or whose row code cannot pick, a conditional when() step, a failed command, or a full list past its page cap. Code stops there and never skips ahead.

What happens next depends on whether the workflow has an agent model (LLM_AGENT in its env file):

  • With one, the agent takes over at the open step. It sees what the earlier steps read and does the open step and the rest (for a named= step it chooses the row or asks the user).
  • Without one, the turn ends as completed. Code writes the answer: what ran (each step, its result, the facts recorded), then where it stopped and why; the remaining steps come back as data a client can show (fw_not_run). In a chat a person answers, two open steps become a question instead: a when() step whose inner step code can run (yes or no), and a run() step missing one plain value (the reply is the value).

A command whose steps code runs to the end, with its answer written by __result__ (see the answer, in code), takes no model call at all. To see where code stops, run fastworkflow command run-code <workflow folder> <command> --input '<json>'. It runs the workflow's real commands, so use a copy of the app's data. It is a second implementation of the step runner, not the runtime itself: it reads only the first page of an all_pages step, does not move to the context a step needs first, and takes an only row without checking for a further page, so a plan that needs either behaves differently there; trust a real run for those. A command of an enclosing record runs on that record there, as in a real run.

The row a listing named: named=

A search lists rows ("find the members called Raj Patel"); the next command needs one row's id, but the user gave a name. run("open_member", named=input.member) opens the row with that name and passes its id. A listing is the Output of a command that returns one list per column, such as member_uids and names, where item i of every list is row i.

  • The id field. At load, the framework picks the Input field a row is opened by: the one field that declares from_command_output (here member_uid, from find_member.member_uids), else the one required field whose name is an id (..._uid or ..._id). Two fields that declare a producer count as none, and the id-name rule decides. With neither, the load of the command that writes the step fails: "declares no row id input ... declare the producer of its id field with from_command_output, or pass the id input explicitly". A required str field with some other name is not enough.
  • The listing. Code looks back over this call's commands, in any phase, for the latest one whose arguments hold that same name (find_member query=Raj Patel) and whose Output has the list of ids that fits the field.
  • The row. Code opens the one row with a cell equal to the name (case, spacing and quotes ignored: "Dune" is not "Dune Messiah"). When no cell equals the name, it opens the listing's only row, even one whose name differs (as "Raj" opens Raj Patel below). When several rows match, or the listing has several rows and none matches, or pages are unread, code does not guess: the step is open.

Picking a row yourself, as in run("open_book", book_uid=find.book_uids[0]), takes the first of several matches without complaint, so two books with similar titles give a confident answer about the wrong one. Use named= (or the only-row rule) whenever the row must be the one the user named.

A listing that can only hold one row needs no name: run("open_member") takes the id from the only row. When your code already knows the id, pass it: run("open_member", named=input.member, member_uid=uid) is simply open_member member_uid=.... Without the id, a named= step takes no other keyword; one fails the load. So does a named= step on a command that requires a second input with no default ("... also requires ..., which such a step cannot pass"): pass the row's id and every required input instead.

Every page of a list: all_pages=True

Some listing commands return one page at a time. When a plan needs the whole list, to count it or name every row, write run("list_loans", all_pages=True) and code reads every page for you. A command is paged when:

  • Its Input has a field named exactly start, typed int or Optional[int]: the position of the first row of the page, where empty or 0 means the first page. No other name works: offset or page is an ordinary field.
  • Its Output has total: int, how many rows the whole list has. Every list field of the Output holds one entry per row of this page, so all of them have the same length. The load does not check the lengths: with lists of different lengths code silently reads one page.

The next start is this page's start plus the rows it returned; reading stops at total or at an empty page. While rows remain, the framework ends the response text with a line such as Rows 1-10 of 23; next page: start=10., but only when the command returns its Output directly: with CommandResponse(output=...) the line is not added, though code still pages by reading the Output. The phase's facts (the typed record a phase hands on, see what a phase hands on) hold every row read, in order, and the one total. Without all_pages the step reads the first page; with start= written, just that page. all_pages=True with named= fails the load: one reads every row, the other opens one. all_pages=True on a command that is not paged is accepted and reads once.

Code reads at most 20 pages of one step, the first included; FW_CODE_MAX_PAGES in the workflow's fastworkflow.env changes that (a value that is not a positive whole number logs a warning and 20 applies). At the cap with rows left, the step is open and the pages read are kept. The agent is told which page to read next, never page 1 again; if it runs out of steps too, the answer ends with a note such as list_loans: 200 rows read of 230 the command reported. With no agent model, the answer adds a Rows read so far section (the rows read of the total, and the first list field of each page). Either way it says any count above is of a partial read, not of the whole list.

Beginner mistakes

  • A misspelled keyword. The framework checks each keyword against the Input at load. run("find_book", title=...), when the field is query, is a load problem of that planning command: "a step passes title to 'find_book', whose Signature.Input has no such field". fastworkflow run_cli, train, the server and command preview --check report it, and the command does not load.
  • Leaning on the only row. run("open_book") after find_book works for "Persuasion" but is open for "Dune", which matches two books. When a search can match several rows, use named=.
  • A named= value that differs from the search. The listing's own search argument must hold the same name. After find_member query=Lee, named="Ann Lee" finds no listing searched for "Ann Lee" and stays open, even though the listing holds only Ann Lee. Pass the same input to both, as note_member does.
  • No total on a paged command. It fails the load: "Input.start makes Book/list_loans a paged command, but its Output declares no total; declare total: int, how many rows there are on every page, or rename start if it is not a page".
  • total set to the page's length. It loads, but code takes the first page for the last and silently counts one page.
