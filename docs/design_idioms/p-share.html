Shared phases

Two planning commands often start the same way: both find a book by its title, then open it. Write those phases once, on a plain base class in a helper module, and let each command's PlanGenerator subclass it. This is ordinary Python inheritance; the framework adds two load checks, below.

The words: a planning command is a command file whose PlanGenerator class lists steps instead of running a body (see a plan in place of a body). A phase is one public method of that class, so every public method on the shared base becomes a phase of every subclass; name a helper on the base with a leading underscore. A forgotten underscore makes the helper a phase of each subclass that writes no __phases__, where a helper that returns no list of steps fails that command's load ("steps() fails on placeholder inputs ... describe is defined on the base BookPhases (_book_phases.py): if describe is a helper, name it _describe"; a declared Signature.template does not hide it), while a subclass whose __phases__ leaves it out loads and never runs it. It returns the steps it runs, each a run("command", ...), and its return annotation is the type of the facts it leaves. A later phase, or __result__ (the method that writes the answer), reads those facts through a parameter with the phase's name. A helper module is a file in _commands/ whose name starts with _: the commands import it, and it is never a command itself (see helper modules).

In the example, BookPhases holds the phases find and book and a __result__. book_by_title subclasses it and writes nothing else: with no __phases__ of its own it runs the base's phases in the order the base wrote them. book_loans adds a third phase, loans, so it writes __phases__(self, input), which returns the phases a call runs, in order, inherited ones included. The framework calls __phases__ several times (to build the template, for the run, and on resume), so it must depend on input alone. Its __result__ extends the shared answer with super().

At run time nothing is different from a command that wrote every phase itself. Running book_loans for "Dune" with fastworkflow command run-code on a copy of the test workflow (no shipped example uses shared phases) runs find_book, then show_book, then list_loans, and answers "Dune is by Frank Herbert; the library owns 3 copies." followed by "It is on loan to 2 borrowers (Ann Lee, Raj Patel)." Each command keeps its own Signature: the base class has none, and the subclass's Input must have every field the inherited phases read (here title). To write those fields once, put a model in the _ module too (class TitleInput(BaseModel) with title) and let each command's Input subclass it: class Input(TitleInput). A missing field fails the load with "phase 'find' fails while its template is built (every fact unknown): AttributeError: 'Input' object has no attribute 'title'".

Two mistakes the loader catches. Each one keeps the command from loading, and it is listed before the workflow starts (see what a mistake stops).

  • A subclass that adds a phase but writes no __phases__. The framework will not guess where the new phase goes: "PlanGenerator adds the phase(s) loans to those of _book_phases.BookPhases: write __phases__(self, input) returning the phases a call runs, in order (from: self.find, self.book, self.loans)". The same holds for a class with phases from two bases. A subclass that only overrides a base phase needs no __phases__.
  • Subclassing another command's PlanGenerator directly instead of a base in a _ module (the check walks every base, so a subclass of a helper that itself subclasses a command's PlanGenerator fails the same way): "PlanGenerator inherits from book_by_title's PlanGenerator; to reuse its whole job, call book_by_title in a step; to share phases, move them to a base class in a _ module". To reuse another command's whole job, call it from a step instead (see calling a planning command). The check looks only at bases named PlanGenerator: subclassing a class with another name in a command file is not refused.

See also a phase that does not run: book returns [] because what find found decides it; a phase an input decides is left out by __phases__ instead.

Other places a subclass matters

Outside phases, subclassing matters to the framework in three more places. Each is taught on its own page.

  • A subclass of an application class. A context (the folder of commands for one kind of object) is named by the object's own class name, never its parents'. So an object of class Paperback(Book) gets none of Book's commands unless _commands/context_inheritance_model.json lists Book as its base. See commands shared through a base.
  • A subclass of the declared Output. A command that returns an instance of a subclass of its Signature.Output directly fails the call ("declares an Output but returned ..."), and so does a subclass instance inside CommandResponse(output=...): the class must be exactly the declared one in both forms. See what it returns.
  • An Input that subclasses another model. It carries the inherited fields and validators, and they are extracted, asked for and checked like fields written in place. See an input.
