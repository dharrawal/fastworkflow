Helper modules

A helper module is a Python file in the workflow's one helper package, _commands/_shared/ (an __init__.py plus modules). Reach for one when several commands need the same code: shared wording, a lookup table, a facts model, or the phases two planning commands share (see shared phases). The framework never treats it as a command, so it gets no seeds, no training and no entry in any command list. Your commands import it like any Python module: from ._shared.wording import copies from a command at the top of _commands/, from .._shared.wording import copies from a context folder. A helper that fails to import fails every command that imports it (each one reported, naming the command file, then the helper file and line the error came from); the other commands load.

FileWhat the framework does with it
_commands/_shared/wording.py, any module of _commands/_shared/Nothing. It is a module your commands import.
_commands/Library/_Library.py, named after its folderThe one exception: the context's own class Context (see a folder for one kind of object). The match is case-exact: a _library.py that defines class Context stops the workflow, naming the file it should be ("the context class file of Library is _Library.py: rename _library.py to _Library.py").
Any other _name.py in _commands/ or a context folder, any other folder whose name starts with _Stops the workflow, one line naming the file and _commands/_shared/ ("_commands/Library/_wording.py: is not read: ... move it to _commands/_shared/wording.py and import it as from .._shared.wording import ..."). A name close to _workflow.py or to the folder's _<Context>.py gets a did-you-mean, so a misspelt settings or context class file is caught. __init__.py and __pycache__ are allowed everywhere. A folder without the _ that holds only helpers stops the workflow too ("the context folder 'shared' holds no command file and inherits none").
_commands/_workflow.py, at the top of _commands/ onlyThe workflow's own settings, the class attributes of its class Context: the request splitter's optional settings (see splitting a request).
_commands/context_inheritance_model.jsonA removed spelling: it stops the workflow. A context's bases are inherits on its class Context (see old spellings).

Some names in the workflow folder itself, beside _commands/, are read by the framework too; do not use them for your own files:

FileWhat the framework does with it
startup_action.jsonNames the startup command (see the root object).
workflow_inheritance_model.jsonThe base workflows whose commands this workflow takes.
_policy/table.pyThe policy table: rules checked when commands run.
personas.jsonWho your users are, for the training requests fastworkflow train generates.
fastworkflow.env, fastworkflow.passwords.envThe default settings and keys files of fastworkflow run (a flag names others; with none here, the folder above is tried).
accepted_duplicates.jsonPairs of commands whose seeds look alike on purpose, read by fastworkflow train (see how a request finds your command).
intent_benchmark.jsonRequests that score routing; fastworkflow train stops when a seed is one of them.
workflow_description.txtWritten by fastworkflow build (a generated description of the workflow; nothing reads it), which overwrites the file.
context_hierarchy_model.jsonNot read: a leftover of an old spelling, warned about once and safe to delete (see old spellings).
___command_info/, ___convo_info/Written by the framework: the trained intent model and its caches, and the conversation stores (the learning store intent_learning.sqlite3 among them). Do not edit them.
