02

Commands shared through a base

Reach for this when two kinds of object need the same commands. In the library example, a book and a member can both take notes. You write add_note and show_notes once, in a folder of their own, and list that folder as a base of both. A context is a folder under _commands/, one per kind of object; the workflow "stands on" a context when the object it is working on is of that kind (see A folder for one kind of object).

The file _commands/context_inheritance_model.json maps a context name to {"base": [...]}, a list of other context names. A context with a base gets every command in that base's folder, and in the base's own bases, as if the files were in its own folder. It shares commands only: the base's class Context hooks (get_parent, get_displayname, get_state and the rest) are not inherited, so each context writes its own. Here, standing on a book, the user can say "add a note: the cover is torn" and Record/add_note runs. workflow.record inside it is the book, so one command file serves books and members alike.

The rules the framework checks when it reads the file:

  • The file holds one JSON object. Each entry must have a base key, and its value must be a list of strings. An empty list means no base and is valid; an entry with no base key at all is an error. Leave a context out of the file if it has no base; contexts are found from their folders, not from this file. Every key must be a context folder, of this workflow or of a base workflow: a key that is none stops the workflow ("the key 'Paperbak' is no context folder"). A context whose commands all come from its bases is a folder with no command file, holding only its _<Context>.py (any file keeps the folder in git).
  • Every name in a base list must be a context folder. "*", the global context, is always accepted; as a base it puts the global commands into the context's own set, so the intent model scores them there too, not only on the way to the global scope.
  • A base may not lead back to itself (Book to Record to Book).

With several bases, they are read in list order, each base's own bases before the next one, and the first command found under a file name wins. fastworkflow build writes this file from the base classes in your application: a rebuild merges: an entry keeps every base it lists, gains the bases found from the classes, and nothing is removed, so a base you added by hand survives. Each entry added or changed is printed.

A file that breaks one of these stops the workflow when it loads, with one message that names the file and the context that lists the base, for example .../_commands/context_inheritance_model.json: context 'Book' declares the base 'Recrod', which is no context of the workflow (...) (see what a mistake stops). A file with only {}, or no file at all, is fine.

A base can be a context that no object ever is. Nothing in the library is a plain Record; the folder only holds shared commands. Its _Record.py says so: occupiable = False tells the framework not to offer Record as a place to move to, and that is all such a base needs: the server's startup check does not list a context declared occupiable = False as one with no way to be saved, so it needs no get_state (the example's get_state returning fastworkflow.EPHEMERAL, below, is not needed; see Remember the object).

Two things beginners trip on. First, a context's own command wins over a base's command with the same file name: if _commands/Book/show_notes.py existed, a book would run that one and never Record/show_notes. Second, the context name is the exact Python class name of the object. The framework does not read your class hierarchy at run time, so class Book(Record) in your application gives Book nothing; only this file does. After you change the file, run fastworkflow train again: the set of commands a context recognises has changed, and training notices.

See also The enclosing record, the other way a context reaches commands it does not hold: those run on the enclosing object, while a base's commands run on the current one.
