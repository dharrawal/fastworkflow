02

Commands shared through a base

Reach for this when two kinds of object need the same commands. In the library example, a book and a member can both take notes. You write add_note and show_notes once, in a folder of their own, and list that folder as a base of both. A context is a folder under _commands/, one per kind of object; the workflow "stands on" a context when the object it is working on is of that kind (see A folder for one kind of object).

A context declares its bases in its own context class: inherits = ["Record"] in the class Context of _commands/Book/_Book.py. A context that inherits another gets every command in that context's folder, and in that context's own bases, as if the files were in its own folder. It shares commands only: the base's class Context hooks (get_parent, get_displayname, get_state and the rest) are not inherited, so each context writes its own. Here, standing on a book, the user can say "add a note: the cover is torn" and Record/add_note runs. workflow.record inside it is the book, so one command file serves books and members alike.

The framework reads inherits as written, without importing the file, and checks it when the workflow loads:

  • It is a list of context names written as string literals, in the body of class Context itself (not inherited from a Python base class). Leave it out for a context with no base; inherits = [] is an error, and so is assigning it twice.
  • Every name is a context, a folder of _commands/ of this workflow or of a base workflow, and is named once. "*", the global commands, is always accepted: inherits = ["*"] puts the global commands into the context's own set, so the intent model scores them there too, not only on the way to the global scope.
  • A context does not inherit itself, and a base may not lead back to the context (Book to Record to Book).
  • A context whose commands all come from its bases is a folder with no command file, holding only its _<Context>.py with inherits. A folder that holds no command file and inherits none stops the workflow.

With several bases, they are read in list order, each base's own bases before the next one, and the first command found under a file name wins. fastworkflow build derives the bases from the base classes in your application and prints one line per context: the inherits line, the file it belongs in, and whether that file declares it, declares something else (not changed) or does not exist yet. It writes the line only into a _<Context>.py it creates itself; it never edits one that exists, so a base you declared by hand is kept.

A mistake stops the workflow when it loads, with one message that names the file, for example _commands/Book/_Book.py: inherits names 'Recrod', which is no context; did you mean 'Record'? A context is a folder of _commands/; the contexts are: Book, Library, Member, Record (see what a mistake stops).

A base can be a context that no object ever is. Nothing in the library is a plain Record; the folder only holds shared commands. Its _Record.py says so: occupiable = False tells the framework not to offer Record as a place to move to (so it declares no parents, and a @descends_to that names it fails the load of the command), and that is all such a base needs: the server's startup check does not list a context declared occupiable = False as one with no way to be saved, so it needs no get_state (the example's get_state returning fastworkflow.EPHEMERAL, below, is not needed; see Remember the object).

Two things beginners trip on. First, a context's own command wins over a base's command with the same file name: if _commands/Book/show_notes.py existed, a book would run that one and never Record/show_notes. Second, the context name is the exact Python class name of the object. The framework does not read your class hierarchy at run time, so class Book(Record) in your application gives Book nothing; only inherits does. After you change it, run fastworkflow train again: the set of commands a context recognises has changed, and training notices.

See also The enclosing record, the other way a context reaches commands it does not hold: those run on the enclosing object, while a base's commands run on the current one.
