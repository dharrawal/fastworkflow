09

Changes data or needs a yes

Some commands are risky to run: they add a note, cancel an order, send an email. fastWorkflow gives you two marks for them, with different jobs.

  • @fastworkflow.writes says "this command changes data". It asks no one. It limits what a planning command (a command that lists steps for an agent to carry out instead of running code; see A plan in place of a body) may run: a step can run it only when the step names it.
  • @fastworkflow.user_approval_for_execution(...) says "a person must say yes first". The framework stops just before the command runs and asks the user.

Put @writes on every command that changes data, even one whose change is easy to undo. Add the approval mark only when the user must confirm each run. Neither mark replaces the other: @writes (the fact that the command changes data) never asks anyone, and the approval mark (who must agree) does not tell the framework the command changes data; the review's "changes data" note, its explicit yes, the look-up-only guard and a policy table's write rules read @writes only. One rule reads both: a command a model chose is confirmed when it carries either mark (below). A command that only reads, or only moves the user to another record, carries neither. Both marks go on the ResponseGenerator of an execution command (a command whose Python code does the work; see One file, two classes). Here is the library example's add_note with both. The shipped file carries only @writes; the approval lines are added to show the second mark.

@writes: the command changes data

The decorator takes no arguments and changes nothing about how the command itself runs. A planning command never carries it: the framework works out that a planning command writes when one of its steps runs a command marked @writes, directly or through another planning command it calls. The framework reads it in four places.

Outside a planning command (a command the user typed, or the main agent answering a request) @writes refuses no call; it only decides whether a model's pick needs a yes. This planning command from the library carries no mark; it writes because a step runs add_note:

The approval mark: ask before it runs

Leave the approval mark off and the command runs whenever the agent (the model that picks and calls commands for the user) decides to call it. With it, the framework stops before the run, shows the user what is about to happen, and waits. The mark takes one of two values of fastworkflow.UserApproval:

  • REQUIRED_ALWAYS: a person confirms every run, even a command they typed themselves (a / message or assistant mode), and it can never be delegated.
  • REQUIRED_UNTIL_DELEGATED: the agent needs the user's say. The user's own typed command counts as that say (its exact name, or a pick at the which-command question; a model's pick from the user's words is confirmed first, as above), and so does a standing always approval, so those runs go ahead without a question. A step of a planning command the user typed is asked about like an agent's call, because the step is the agent's.

What the user sees, word for word: "The agent wants to run Record/add_note with text=card renewed. Reply yes to approve or no to decline. You are asked every time." For a REQUIRED_UNTIL_DELEGATED command the question ends "Reply yes to approve, no to decline, or always to approve this command from now on." The question never says whether the change can be undone, because the framework does not know; if your users should read that, write it in approval_template. When the user typed the command, it opens "You asked to run" instead. The part after "with" lists the parameter values. The optional approval_template string on the class replaces it with your own wording, filled from the values like str.format; a template that does not fill falls back to the list. The template is checked when the files load: a name in braces that is not a field of Input, or a template on a command with no approval mark, fails the load of that command (see what a mistake stops).

The reply is read whole. A yes (yes, true, ok, agreed, accept or go; case and a trailing . or ! are ignored) runs that one call, once, with the values shown. no, read the same way, declines and nothing runs. always is offered only for REQUIRED_UNTIL_DELEGATED: it runs the call and records a standing approval for that user, workflow and command, so later agent calls run without a question. A REQUIRED_ALWAYS question does not offer always; typing it anyway is not read as a yes, records nothing and gets the question again. Anything else gets the same question again too. A standing approval recorded earlier for a REQUIRED_ALWAYS command is ignored, though it still shows in /approvals and /revoke_approval removes it. The user lists standing approvals with /approvals and removes one with /revoke_approval <command>; /cancel_pending drops the question. The question expires after 2 turns or 15 minutes, and if the values changed since it was asked, the call is not run.

One limit, and one refusal. The setting FW_APPROVAL_BINDING turns every approval mark off for the whole process: off asks nothing, shadow records each decision but runs the call (the default is enforce). And the gate does not run a call it cannot check: when the workflow's routing or a command's mark cannot be read, or a short name matches several commands one of which carries a mark, the call is refused with a message ("... that name matches several commands (...) and one of them needs your approval. Call it by its full name.").

One question is out at a time. When no person can answer (an unattended run), the call is not run, nothing is kept waiting, and the caller reads "Record/add_note was not run: it needs your approval, and no one can give it on this turn. Run it again when you can answer." A standing approval does not change that for a REQUIRED_UNTIL_DELEGATED command, unless the server verifies who each end user is; for a REQUIRED_ALWAYS command it never does. A second call that needs approval while one question is open is not run either: "Record/add_note was not run: it needs your approval, and another approval is already waiting for your answer. Answer that one first, then run it again."

Beginner mistakes

Forget @writes on a command that changes data, and the framework treats it as read-only: an agent working through a planning command that only looks things up may run it unasked, a model's pick of it runs with no yes, and the review does not warn the user. The guard, the note and the yes are only as complete as the marks and the step names. Some shipped examples that change data carry no mark (the messaging apps' send_message, simple_workflow_template's mark_as_complete, add_child_workitem, remove_child_workitem and remove_all_child_workitems); do not copy them.

Put @writes on a planning command's PlanGenerator, and that command does not load: "a planning command cannot carry @writes ... put the decorator on that execution command". The old spelling, a class attribute writes = True, also fails the load of its command and names the decorator.

Put the approval mark on a PlanGenerator, and the command fails to load with "a planning command cannot carry @user_approval_for_execution. Its steps are asked about when they run a command that carries it: put the decorator on that execution command". Both marks follow one rule on a planning command: it needs what the commands its steps run need, directly or through another planning command it calls. The command lists mark it "(needs your approval before it runs)" when a step reaches a REQUIRED_ALWAYS command, else "(may need your approval)" when one reaches a REQUIRED_UNTIL_DELEGATED command. The planning command itself is never stopped; each such step's call is asked about.
