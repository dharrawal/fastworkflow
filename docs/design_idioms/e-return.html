What it returns

Every execution command says what it gives back with an Output class, and its code returns one. Output is a Pydantic model you nest inside the command's Signature class (the class that describes the command; see one file, two classes). Reach for it in every command that answers with data: it is how the agent, a client and a later step all get your result without reading prose.

The one form to write: declare Signature.Output, give __call__ the return annotation -> Signature.Output (for you and your editor; the framework finds Output in the module, not in the annotation), and end __call__ with return Signature.Output(...). __call__ is the method of ResponseGenerator that the framework calls to run the command. The example below is the library example's book search.

What the framework does with the returned Output:

  • The response text is the Output as JSON. That text is what the agent reads, and what a person sees in assistant mode. When the command reads one page of rows (its Input has an int field named start, and its Output has a total and list fields of one length) and rows remain, the framework adds a line such as Rows 1-20 of 57; next page: start=20. It adds it only when __call__ returns the Output itself, not inside a CommandResponse.
  • The instance itself is kept beside the text. GET /command_schemas publishes the Output JSON schema, descriptions included. A per-command MCP tool, with the schema and the instance as its structured result, exists only in the example MCP server (fastworkflow/mcp_server.py); the shipped run_fastapi_mcp server exposes turn tools, and the Output arrives inside the turn's command outputs.
  • A planning command can read it with no parsing. A facts field typed find_book.Output is filled with this command's Output from its run (see what a phase hands on), so the ids, labels and counts arrive exactly.
  • Two or more list fields that are the columns of one table share a ui table group, as above. A client such as the chat page may draw them as one table. Without the hint, fastworkflow command preview --check prints a notice. The other display hints are taught at the end of this page, how a result is shown.

To decline, raise fastworkflow.Refused("message") instead of returning (see correct or refuse). The user is told the message and the command counts as failed. Build a real Output on every path that does return, including "found nothing" (an empty list and a total of 0), so a caller can rely on it.

Two other returns exist, for narrow cases. Return fastworkflow.CommandResponse(response=..., output=Signature.Output(...)) when the agent should read your own sentence instead of the JSON, or when the command also hands the client artifacts (a dict) or next_actions. The Output still rides along in output. A plain str is accepted only from a command that declares no Output; it is text and nothing else, so no later step and no client can read a value from it.

Beginner mistakes, each a call error that names the command: returning a str, a dict or a CommandResponse with no output from a command that declares an Output ("find_book declares an Output but returned str; return the Output, or CommandResponse(response=..., output=<Output>)"); returning an instance of a different model, even a subclass of Output, whether directly or inside CommandResponse(output=...) (the class must be exactly the declared Output); building a CommandOutput yourself; and setting success=False on a CommandResponse (success is the framework's to set; refuse with Refused). Declaring Output as a subclass of another model is fine: fastworkflow/examples/extended_workflow_example/_commands/WorkItem/get_status.py writes class Output(BaseSig.Output) with two more fields and returns its own Signature.Output(...).

A planning command's __result__ follows the same rule, with the same errors: when the command declares an Output, it must return that Output, alone or inside CommandResponse(output=...), and returning text is an error there too. Output is a command's public result in both kinds. A __result__ that raises, returns None or returns anything else fails the command; fastworkflow.planning.ANSWER_BY_MODEL is the one way to leave the answer to a model, for a command that declares no Output: one that declares an Output and returns it fails the call (see the answer, in code).

See also one file, two classes, correct or refuse, what a phase hands on, every page of a list.

How a result is shown

A display hint is a small note on an Output field, written as json_schema_extra={"ui": {...}}, that tells a client how to draw the value: leave it out of the view, show it first, format it as money, put it in a table. Reach for one when a result looks wrong on the chat page, for example a list of ids in the way.

A hint never changes what the command returns. The value is still in the Output, in the response text the agent reads, in the structured result an MCP client gets, and the schema that GET /command_schemas publishes carries the hint itself under the key ui. No check, extraction or plan reads it; a client may follow it or ignore it. Specifically, hidden hides the field from what the chat page draws (the result card and the composed answer card, and the result data the model that writes the card reads leaves it out; that model also reads the turn's answer text, which may quote the value, and a quote of a hidden value of 6 or more characters is screened out of the card afterwards). It does not hide it from the agent, from an MCP client or from the JSON. To keep a value out of the agent's text, return CommandResponse(response=...) with your own sentence, as the figure below does.

The keys, what they fit, and what the chat page does with them:

HintFitsThe chat page
"hidden": Trueany Output fieldLeaves the field out of the result card, the stat strip and tables, and the composed answer card.
"hero": Trueone value (str, int, float, bool)Puts it in the highlighted strip at the top of the card. With no hero, the page picks up to four short values itself. Not allowed with table on one field.
"format": "currency"int, floatShows two decimals; with "currency": "USD" (a three-letter code, either case) it shows the currency symbol too. currency needs this format.
"format": "percent"int, floatAdds a percent sign: 12 is shown as 12%.
"format": "code"str (any scalar)Shows it in a monospace style, for ids, paths and commands.
"format": "badge"str, Literal, Enum, or a number (without tones)Shows a coloured label. With "tones": {"delivered": "good"} you choose each value's colour from good, warning, bad, neutral; a value you leave out gets the page's own guess. tones needs this format, and on a Literal or Enum every key must be a declared value.
"table": "name"a list of str, int, float, bool or LiteralThe list fields that share a group name are the columns of one table, as in find_book above.

format can also sit on a list column of a table group. With no hint at all, the page decides from the value's type: numbers get thousands separators, bool is shown as yes or no, a list is drawn as bullets, a list of objects as a table, and the field's name never changes how it is drawn.

The table group rule. Give every column of one table the same group name, in the fields' order. A group needs at least two list fields, and at least two of them not hidden. The results panel of the chat page draws a table only when every column in the group is present and has the same length; otherwise it draws each list as bullets and never trims or pads, and it never guesses columns from equal lengths alone. The answer card is different: it infers a table from any output that has an integer total and scalar lists of one length, and it ignores a declared group. That difference is known and under review.

Mistakes and what you see. A mistake in a hint is not silent. A badge on a number is allowed: a score drawn as a badge is a presentation choice.

  • Two or more visible list fields and no table group: the page draws separate lists, and fastworkflow command preview --check prints a notice: naming the fields. Nothing fails. If they are not columns of one table, ignore it.
  • A hint on the wrong kind of field (table on a str, tones on an int, currency on a str, a tones key that is not a declared value, hero on a list, format: "percent" or "currency" on a non-number, a key that only an Input field uses on an Output field), a format that is not one of currency, percent, code, badge, "hidden": False (leave the key out instead), a misspelt key (hiden gives "did you mean 'hidden'?"), or a widget on an Output field: the command does not load, and fastworkflow run_cli, train, the server and fastworkflow command preview --check list it with the file and the field (see what a mistake stops).
  • The same hints on an Input field (except widget, see an input) fail the load the same way.

The three id lists are still in the Output, so a later step can read them; the chat page shows only order_details. This command also returns CommandResponse(response=...) with just order_details, so the agent's text leaves the lists out too. The shipped examples use only hidden and table; the other hints are covered by tests, and you add them the same way.
