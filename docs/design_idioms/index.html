For people writing a workflow

The shapes a workflow author writes.

A fastWorkflow app lets people, or an AI agent, use your Python application by asking in plain words. You write commands. Each command is one Python file under _commands/, and the framework picks the command a message means, reads the values it needs out of the message, asks for any that are missing, and runs it.

There are two kinds of command. An execution command runs your own Python code once. A planning command runs other commands as a short list of steps, and the framework's code runs every step it can. A context is one kind of object in your application, such as a book or a member: a folder under _commands/ named after its class, holding the commands that act on that object.

How to read this site: start at One file, two classes and follow the pages in order. There are 23 idioms in three groups: execution commands, planning commands and contexts. Each page is one shape you write, says when to reach for it, and shows a real example, most of them from the shipped library example (fastworkflow/examples/library). A real command file uses several shapes at once.

Five reference pages sit beside the idioms. How a turn runs follows one user message from start to finish: how it is split into parts, the questions it may ask, the one review and the run. Plain Python, read by the framework is one table of the ordinary Python and Pydantic forms (a class, a docstring, a Field, an annotation, a union, a property, a subclass) that the framework reads, each with the page that teaches it. The other three are Helper modules, Planning step helpers and Load errors: one rule, and the removed spellings.

Execution commands

Code that runs.

One Python file with two classes. Signature describes the command: what it does, example requests, the values it needs and what it returns. ResponseGenerator runs your code. An execution command runs in agent mode, in assistant mode (fastworkflow run_cli --assistant), and when a client calls it directly over HTTP or MCP.

Planning commands

A job written as steps.

Same folder, same Signature. A PlanGenerator takes the place of the ResponseGenerator. Each of its methods without a leading underscore is a phase: it returns the steps of one part of the job, and its return annotation says which command results (the facts) that phase hands on. Phases run in the order the methods are written; a phase with nothing to do returns []. A method with one leading underscore is a helper, and __result__ writes the answer.

Write a planning command's Signature docstring with care: besides describing the command everywhere, it is the line the request splitter reads for that kind of job (see how a turn runs).

Contexts

Where a command lives, and which object it acts on.

The workflow always stands on one object of your application, workflow.record, and offers the commands in the folder named after that object's class. Its class Context, in _commands/<Context>/_<Context>.py, lets it reach more. inherits = [...] gives a context other contexts' commands. get_parent names the object that encloses this one, and parents = [...] names the contexts that object can be.

Where a request looks. This is not a separate shape; it follows from the pages below. A command name typed exactly is found in the nearest place that has it, in this order: the current record's own context, the contexts it inherits, then each enclosing record reached through get_parent (with the contexts it inherits), up to the root object, and last the global commands, the files directly in _commands/ (for plain words, a trained global model is asked first). A command runs on the record where it was found, whether a typed or plain-words request or a direct action from a client reached it. The workflow moves onto another record only when a command assigns workflow.record, and @descends_to tells the framework which command does that (see the record it acts on).
