Calling a planning command

A step of one planning command can run another planning command. Reach for this when a job you need is already written as a planning command and you want it done whole, the way that command does it. In the library example, "who has borrowed Dune?" first needs the book found and opened. book_by_title already does that, so book_loans calls it as one step and then lists the loans.

A planning command is a command whose PlanGenerator class lists steps instead of running code (see a plan in place of a body). Each method of PlanGenerator is a phase, and a phase returns its steps as run(...) calls (see a step the code runs). Calling a planning command needs nothing new: write run("book_by_title", title=input.title) exactly as you would name an execution command. When the files load, the framework checks that the name is a command of the workflow and that every keyword is a field of that command's Input.

The phase's return annotation, -> BookByTitle.Output, says what the phase hands on to later phases and to __result__: the called command's Output, its typed result. BookByTitle is just book_by_title's Signature class, imported from its file. So the command you call must declare an Output class in its Signature and fill it from its __result__ (see the answer, in code and what it returns).

At run time the called command runs its own phases, in a frame of its own, and its answer and Output come back as the result of your one step. Its inner steps (find_book, open_book) stay inside it: your phase sees only its Output. The workflow is left where the called command left it. book_by_title opened the book, so the next phase runs list_loans on that book without naming it (see move onto a record). When the called command may open nothing, test its Output before relying on where it left the workflow, as if not book.found: return [] does below; otherwise the next phase runs on whatever record was open before.

A call that fails does not end the turn. A refused argument, a called command that fails, or a spent step budget gives your step a failed result with the reason. With an agent model the agent then carries on with the remaining steps. With no agent model the failed step is an open step, and a stop inside a called command stops the command that called it, with what ran so far. The step budget is FW_TURN_MAX_STEPS in the workflow's fastworkflow.env, 400 when unset: every step the model takes inside nested calls during one turn counts against it; steps that code runs do not count. Once it is spent, each nested call fails with "The step budget for nested commands is spent; continue with the remaining steps directly."

Two beginner mistakes, and what you see:

  • A command that calls itself, directly or through others (book_by_title calling book_loans, which calls book_by_title). Every command on the cycle fails to load, each listed with "a planning command cannot call itself, even through others: Library/book_by_title -> Library/book_loans -> Library/book_by_title" (see what a mistake stops). A step written as text whose first word is the planning command's own name is read as a call of itself, so it fails the load too ("a planning command cannot call itself: Library/book_by_title -> Library/book_by_title"). fastworkflow command run-code stops on a cycle with "calls itself through its steps (a cycle)". If a running agent still names a command that is already running, that step is refused with "... is already running; call its steps directly." The load resolves a step's command name as the runtime does, nearest scope first on the command's own lookup path, so a command that shadows a base's or the global command of its name and runs that name calls itself and fails the load. A name off that path resolves when exactly one command of the workflow has it. The run-time refusal is the only check of a cycle through a name that is on no scope of the path and that several contexts off it have: that cycle loads and is refused at run time (a name no command has fails the load). The rest of the workflow loads.
  • Annotating the phase with a type from inside the called command, such as -> OpenBook.Output. Your phase does not run open_book, so the load reports "phase 'book' hands on open_book's Output, but none of its steps runs open_book". Hand on the called command's Output, and put anything else you need into it.

See also shared phases, which reuse part of a plan as code instead of calling a whole command.
