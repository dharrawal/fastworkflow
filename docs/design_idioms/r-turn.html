How a turn runs

A turn is one user message and everything the framework does to answer it. This page follows one turn in order, so you know what your users will see. You write nothing to get any of it; the last section lists the few things your code influences.

A part (or sub-task) is one of the separate requests a message holds. Each part is bound to one command: an execution command runs your Python once, a planning command runs a list of steps.

A message that goes straight to one command

A message in assistant mode (fastworkflow run --assistant) or one that starts with / is not split and never reviewed. It goes to one command and runs, and when it needs to it asks the same kinds of question as step 2, worded a little differently: with one candidate command, or when a model or a misspelling of its name alone chose a command that changes data or carries an approval mark and that command's approval question will not be asked, it asks "Did you mean the command 'X'?" (answered by its name, a yes (yes, true, ok, agreed, accept or go, the whole reply) or cancel) because there is no review to confirm it, and a missing value of an execution command is asked, with or without an agent model, in the longer form that question takes (the values extracted so far, how to abort). A reply to that value question that the remote model reads as a different request is not run: the question comes back once saying so (to run it, cancel, then send it), and a second such reply in a row ends the command. On the agent-mode path such a reply drops the part at once, and on a plan's decision step it ends the command at that step; neither is run. When nothing matches, it asks which of every command is meant. A planning command that needs the agent is refused on such a message whenever an agent model is set, fastworkflow run --assistant included. A message sent with a chosen plan (use_plan, over HTTP or MCP) is not split either. Everything below describes the agent-mode turn as the terminal (fastworkflow run), the chat page and the HTTP and MCP servers run it: on the terminal each question of steps 2 and 3 waits for the next line typed, which is its reply, and //cancel cancels it. fastworkflow run with no agent model starts in assistant mode, so the no-agent-model sentences below apply to the chat page, HTTP and MCP.

1. Split the message into parts

Users often ask for several things at once: "Show Ann Lee's loans, and who has Dune out?" One call to the planner model (LLM_PLANNER) lists the parts. Earlier turns are background only, never parts. The framework then joins parts that are steps of one job ("find Dune, then open it") and joins a part with no record of its own, or with the same records as the part before it, to that part; with JEV_API_KEY set, the remote model decides whether such a part joins or stays apart. The rest of the clean-up is code, with or without the key: a part wholly in brackets, or one quoting a value or a record the message does not hold, is dropped; a part that only repeats another is dropped; parts that compare records are joined; a sentence that asks nothing is written before the job it is about; a limit sentence ("Do not apply anything.") is added to the parts it applies to; a job the model left out is put back; and a part asking the same thing of each of several records becomes one part per record. Also with the key, the remote model works out which record a part that says "it" or "that account" means and the record is written into the part; with no key nothing is written into such a part. When everything joins back into one job, the user's own words run. There are at most 10 parts. A reply cut off at its output limit is never used; a complete reply is, including the model library's own second try inside the same call. When no complete reply gave a split, the splitter is asked once more without its reasoning; a split that is visibly broken is also asked once more, and when both are, the less broken one is used. If splitting still fails, the message runs whole as one part, and the failure is recorded on the turn's span (subtask_split.failed) and in the log.

2. Resolve every part, before anything runs

Before the split, in a workflow that has planning commands, a request that only asks what the workflow can do is answered by code and no part is made. A single part that names a command by its exact name is resolved here like any other: a value it lacks is asked before it runs, and it then runs with no review.

For each part, in order, the framework decides which command serves it: its exact name, a misspelling of a whole command name (a request that only begins like a name is not one), the trained local intent model when confident, then the remote model when JEV_API_KEY is set; a planning command the local model alone picked is confirmed by the remote model or asked. A name that only another context owns gets a routing hint on the "/" path only; here the part is treated as one no command serves (below). Only when it still cannot tell does it ask the which-command question: "More than one command fits part 2: ... Which one is meant?", with numbered choices. The reply is read for a pick: a command's name, its last part, a listed number or a misspelling of a whole name (two that fit equally well are unclear), or none ("you misunderstood" too, as the whole reply) or cancel. Only a pick settles the part's command. cancel drops the part. After none or a second reply that cannot be read, the part is treated as one no command serves, so even a one-part turn is reviewed. With one candidate there is no question: the part is bound to it and the review below confirms it.

Then, if the part's command still lacks a required value (a planning command always, though with an agent model only when its values were drafted, FW_DRAFT_ARGUMENTS, on by default; an execution command when no agent model is set, whether the user named it, the local model was sure of it, or it was picked at the which-command question), it asks the missing-value question, one question naming every missing or refused value ("... your request does not give the member. Which member should I use?"). A value an earlier part produces is never asked for. The asking rule is the same everywhere: it keeps asking while each reply fills or fixes a listed value, a reply that makes no progress is asked once more, and the second one in a row stops. A reply that asks for a moment ("wait a moment") gets the same question again, on this question, on the "/" path's parameter question and on a plan's decision step alike: the first in a row counts nothing, each further one counts as a reply with no progress. Both questions end with "Only your answer is read; anything else in the reply is ignored." The framework's phrases for abort and "you misunderstood" count only as the whole reply, so a value that begins like one ("none", "Terminator") is a value, and none leaves an optional value empty. cancel drops that part; the later parts go on. A value is not asked for when the refusal names no value (a rule of the command, for example "the note must not repeat the member's name"): with no agent model the part is not run and is reported as not run with that rule's own message; with an agent model the part stays and the run hands it to the planner or the agent. A part that no command serves is planned by the agent when there is one; with no agent model the user is asked which planning command should run it.

3. One review of the whole turn

Now nothing is missing: every part has its command and its values. The user sees the whole turn once and replies.

Each line is a part's text, then the drafted values in parentheses as input name: value. A part whose command changes data ends with - changes data. When an agent model is set and the workflow has a command that changes data, a part no command serves (the agent will plan it) ends with - may change data, since code cannot tell what the agent will call. When any part carries either mark, the instruction line ends with "This request changes data, so I need an explicit yes to run it." (or "may change data"). The replies it reads:

  • yes runs every part as shown. On a read-only turn "go ahead" and "looks good" also run it. When any part changes or may change data only an explicit yes (yes, true, ok, agreed, accept or go, the whole reply, ignoring case and a final period or exclamation mark) runs it: any other reply that would have accepted, such as "do it" or "no changes", is asked again with that sentence, and once 8 replies have not ended it, the next reply that is not a yes or a no ends it with no run. A review not answered within 30 minutes expires too. A reply that starts with an accept and adds something the plan already does ("yes, but only list them, do not change anything") is an accept too when the reader finds no change in what follows; on a turn that changes data it is still asked again for the plain yes.
  • no (or "cancel", "never mind") runs nothing.
  • step N: use NAME binds part N to another command (book_by_title or Library/book_by_title) and drafts its values again.
  • A correction in plain words ("drop the second one", "the title is Emma") is turned into edits and shown back ("I read your reply as these edits") for an accept; edits that change nothing are never shown back. Edits the review cannot apply (an input the part does not have, a value outside its choices, a part number that does not exist) are read once more with the reason before you are asked; a part number you write ("step 3's title ...") wins over the reader's; and an edit that would copy one of a part's values into an input your reply does not name is left out, and the read-back says so. One that cannot be read gets the typed forms (change N: inputs=key=value, drop N, ...); change N: inputs=key= removes the input. When two marked inputs of a part hold one value you wrote once, the part shows the optional one removed with a note, because that is how it runs.
  • A reply that asks only to look a part up binds it to a command that does not change data; the part then ends with - look up only and never runs a command that changes data, so a turn whose only part that changes data was looked up asks the read-only turn's question (no explicit yes needed).

When there is no review. The turn runs straight away when it is one part that names a command exactly; when it is one part the local model, or a misspelling of its name, gives an execution command that does not change data, or whose approval question will be asked anyway (a planning command, or a command that changes data or carries an approval mark, that a model or a misspelt name alone picked is reviewed); when it is one part whose command the user picked at the which-command question; when the client chose the plan with use_plan (that plan's value question takes the review's place); when nobody can answer (an unattended turn, or REST and MCP, except no-agent mode with a verified end user); and when no agent model is set and nothing would run. Everything else is reviewed, everyday one-part requests included; no command can turn it off.

4. Run

The parts run in order as accepted, and the answer covers each one. No more which-command or value questions are asked, except a decision step inside a running plan and the agent's own questions and approvals. When the agent plans a part, its finish is checked against its own text plan: a step it did not do sends it back with a note.

The workflow's settings are the class attributes of class Context in _commands/_workflow.py: the whole workflow is a context with this one settings file, and Context holds split_examples, identifier_patterns and subject_hints and nothing else (a context hook such as get_parent stops the workflow: the workflow has no parent). Mistakes a beginner makes with _workflow.py: writing the settings at module level instead of in class Context (the load says so), or in the removed _split.py (it stops the workflow, naming _workflow.py); putting it in a context folder (only _commands/_workflow.py is read; any other is ignored, and the workflow load reports it: "the workflow settings are read only from _commands/_workflow.py"); editing it while the server runs (it is read once per process, so restart); and trying to add a rule by writing a Signature class in it. The splitter's rules are the framework's and cannot be replaced: such a class stops the workflow ("a Signature (a replacement splitter prompt) is removed: write split_examples"). Show the rule with an example in split_examples, and steer with the planning commands' docstrings. And if a request you expect to run straight away is reviewed, write a clearer purpose sentence or better seeds so the local model is confident (this helps only an execution command that does not change data, or whose approval question is asked).
