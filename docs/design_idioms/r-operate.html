Train and run

Two commands turn your workflow folder into something people talk to: fastworkflow train builds its local intent model, and one of three run commands serves it. This page says what your choices change in each, and which run command to pick. The full options are in fastworkflow <command> --help and the README.

Train: one command, it decides what to redo

fastworkflow train ./my_workflow ./fastworkflow.env ./fastworkflow.passwords.env

Run it after any change to the workflow; it works out what changed and does only that. In order, it:

  • stops on a command file that does not load, naming the file and the problem, before any training work (the same check run_cli and the server make at start);
  • checks that every command has seed utterances and that no two commands offer the same capability;
  • generates more phrasings of each command's seeds with LLM_SYNDATA_GEN, reusing the cached ones for every command whose seeds did not change, so an unchanged command costs no model call;
  • fits the local intent model: by default an embedding head, which takes seconds, is the same on every run with the same rows, and needs no GPU;
  • trains the framework's own built-in workflows first when they need it. You never train those yourself, and fastworkflow train on the fastworkflow package itself is refused.

What decides your intent model is what you write: each command's purpose sentence, its name and its seed utterances, which count three times. Edit those, then train. --regenerate-utterances is the only override: it ignores the caches and calls the model again, which costs money and changes the generated rows, so use it only when you suspect a cache is wrong. The training report lists the pairs of commands the model confuses most; fix a pair with seeds that tell the two apart, or by merging the commands.

A server already running picks up a retrained embedding head within a few seconds, with no restart. The workflow and per_context layouts (INTENT_MODEL_LAYOUT) need a restart.

Run: pick the command by who is talking to it

All three run the same engine, so a turn does the same thing in each (how a turn runs). What differs is who answers the turn's questions and how they reach it.

CommandForWho answers questions
fastworkflow run_cli <workflow> [env] [passwords]Trying your workflow in a terminal, one user.You: the next line you type is the reply. //cancel cancels what is waiting; Ctrl-C or --timeout_seconds N stops waiting on a turn (it finishes in the background, its output discarded).
fastworkflow run_chatbotDeveloping and debugging in a browser: a workflow picker, a chat, and a trace viewer of what each turn did (which command, which values, which model calls).You, in the page, which shows each question, review and approval with its choices. It starts a local run_fastapi_mcp server for you, on loopback only.
fastworkflow run_fastapi_mcp <workflow> [env] [passwords]Production: an HTTP service with MCP tools, JWT sessions and streaming, for your own front end or for another agent.The client: a turn that asks comes back waiting, and the client's next message is the reply (cancel_pending drops it). With nobody to answer (REST and MCP), the turn's review is skipped, except in no-agent mode with a verified end user.

Agent or assistant. Each run command uses the agent when LLM_AGENT is set. run_cli --assistant (and /invoke_assistant on the server) runs deterministic mode instead, and a single message that starts with / runs deterministically in any of the three. With no LLM_AGENT the workflow runs in no-agent mode, which needs JEV_API_KEY: with neither set, the run commands refuse to start and say why. So does a workflow with no trained local model and no JEV_API_KEY. At start, each prints one line naming how intent is decided (the local model, the remote model, or both).

What this means for your code

  • Nothing in a command depends on the run command. Return your answer from the command; never print it or read from the terminal, or it will not reach the chat page or a server's client.
  • A question your command needs answered is the framework's (a missing value, an approval), never your own prompt, so every run command can ask it.
  • Train before you run, and train again after you edit a command, its seeds or its purpose sentence.
