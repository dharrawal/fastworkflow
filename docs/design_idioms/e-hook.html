Correct or refuse

Sometimes a value is the right type but still not usable: a name typed in the wrong case, an end date before its start date, a request about "everyone" for a command that handles one person. Reach for this shape when your command must fix such a value, or turn it down with a clear message, before its code runs.

The shape is one method on the command's Input class (the pydantic model that lists the command's parameters, see an input), decorated with @model_validator(mode="after"). The framework calls it after it has read the values out of the user's request. In the method you do one of three things:

  • Accept. Return self.
  • Correct. Assign a better value to self.<field>, then return self. Your command's code reads the corrected value.
  • Refuse. Raise fastworkflow.Refused(message, field=...). The message is what the user reads, so say what is wrong and what a good value looks like.

What the user sees. A refusal that names a field (field="user_name", or a list of names) means "this value is wrong, but an answer can fix it". The framework clears that field, keeps the others, and asks for it again, showing your message (it asks the user, or in agent mode the agent that made the call). Their reply is checked again, your validator included. A refusal with no field means "no answer can fix this call". Nobody is asked: the command ends and the user sees your message as a failed result. When the values came from the model that reads the request, a refusal that names a field first makes that model read the request once more, with your message after it, so the message helps it pick a better value for that field (only the fields you named are taken from its second answer). A refusal with no field is not read again: the model is never asked to rewrite values nobody asked about. A @field_validator on one field that raises ValueError or AssertionError is a refusal of that field, exactly as Refused(message, field=<that field>); so is one that raises Refused(message) with no field: the field is the one the validator is on, and it is asked again. A field that names no field of the Input is a bug: on an execution command the call fails with an error naming the field and the Input's fields.

A correction is kept only when the validator passes. If you assign a value and then raise Refused, the assignment is thrown away and the values stay as they were before your method ran. A value a validator corrected is noted "(validator)" in the call's notes on a planning command; on an execution command the extraction span records it as validation_hook.changed_fields.

The same method works for a planning command. A planning command (a command that writes the steps of a job, see a plan in place of a body) has the same Signature.Input, and its validators run on its arguments the same way. The difference is what a refusal with no field leads to: the call is handed to the planner or the agent instead of ending with your message (with no agent model set, that part of the request is not run).

What the method can read. Take a second argument, info, when you need it. info.context["workflow"] is the running workflow, and .record is the object the command acts on (while the framework renders a planning command's plan without running it, the workflow itself is None; fastworkflow command run-code runs the plan and passes the session's workflow, as the runtime does). info.context["command_text"] is the user's request, with their replies to earlier questions after it. info.context["command"] is the command's full name. Without info, write def rule(self). Write mode="after": a model validator in mode="before" or "wrap" makes pydantic validate the whole Input in one call instead, and a ValueError it raises then reaches the user as "the arguments break a rule of <command>: ..." rather than as your bare message, so the command does not load: "Signature.Input: model validator 'tidy' is mode="before"; an Input's model validators must be mode="after"".

What already ran. Your method runs after every other check, the marked fields' check that two of them do not hold the same value included, and nothing checks a value it rewrote again. Every required field is present and of its declared type, and the field's own options and pattern have passed. So check only what the field declaration cannot say: a rule across two fields, a fact about the current record, a cleanup of the text.

Beginner mistakes.

  • Forgetting return self. Returning anything else (including None) is a bug in the command, and the call fails with an error that says the validator must return self.
  • Raising a plain ValueError or AssertionError. It is read exactly as fastworkflow.Refused(message) with no field, and the user reads the bare message, so it works, but raise Refused so the intent is plain and so you can name a field. Any other exception is a failure of the validator: it is reported as "a validator raised KeyError: ..." on a planning command and as "Exception in X's validators: ..." on an execution command, with no field to ask about.
  • Reading info.context["workflow"].record in a planning command without checking it. The workflow itself is None while the framework renders the command's plan without running it, so reading .record raises there: fastworkflow command preview then renders that plan with your validator skipped and a note that says so, and the plan template the planner reads leaves that combination out. Return self early when info.context["workflow"] is None.
  • Raising Refused(message, field=...) from the command's own code (ResponseGenerator.__call__, or a planning command's __result__) to have a value asked again. There the command has already run, so nobody is asked: the refusal is the call's failed answer, and the fields you named are reported on it as its artifact refused_fields. Refuse a value in a validator to have it asked again.
  • Writing the old validate_extracted_parameters method on Signature. It is removed: a command that still has it does not load, and the load error names this shape (see removed spellings).
