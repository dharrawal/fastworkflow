Identifier formats

Most applications name their records by ids with a fixed shape: an account acct_4421, an order #W0000000. Reach for this page when users type such ids in their messages and you want the framework to recognise them. There are two declarations, and they do different jobs.

  • One field's format: pattern= on the field. Use it on every input whose value must have a given shape. The framework refuses a value that does not match the whole pattern, on every path (the "/" path, the plan review's draft and a typed planning call alike), so "xx acct_1 yy" never passes acct_[0-9]+; the question back to the user names the field, the value, the pattern and, when the field has an example, its first example. The model is also told the pattern. A compiled pattern (pattern=re.compile(..., re.I)) keeps its flags. A pattern only validates: it neither adds nor lifts the strict check that a value must be written in the user's message, which only copied_from_command_text asks for (see the request's own words). The field is taught under an input.
  • The workflow's id formats: identifier_patterns. A list on class Context in the optional file _commands/_workflow.py at the workflow root (the workflow's own settings), one compiled pattern per id format. The framework searches the user's message with it, so it finds ids anywhere in free text.

What the framework does with identifier_patterns:

  • Splitting a message. When one message holds several requests, the framework cuts it into parts (see splitting a request). Each id it finds is treated as a record the message names, like a quoted name, so the parts are cut and joined around the right records. When a part says "it" or "that account" and JEV_API_KEY is set, the ids are among the records it may stand for.
  • A cut id becomes the whole id. When the model fills a str input that is marked copied_from_command_text or record_named_in_command_text with "4421" and the message writes acct_4421, the value becomes acct_4421, and only then is the field's pattern checked. If "4421" sits inside two different ids, the value is refused. A value that is not inside an id must be written as whole words: "dun" is not written in "dune". This holds for a marked field of an execution command and of a planning command alike (a command whose body is a plan, see a plan in place of a body); a field with no mark is never widened, because its value is not compared with the message at all.
  • Policy rules. A policy table (_policy/table.py, rules checked when commands run) needs to know which arguments are ids. When the table's own id_patterns is empty, it takes these patterns, flags included. Declare them here once rather than in the table. The policy matches a whole argument value against them, while the split, the referent and the widening search inside the text; an unanchored \b... pattern works both ways.

Without the file nothing breaks: the framework knows one id shape of its own, a UUID or a run of 24 or more hexadecimal digits, which the split counts as a record the message names (it is not used for widening), and it still finds quoted and capitalised names. The file is read once per process, so restart after an edit.

Which to write. Both, when an id is both a field's value and something users type among other words: pattern checks one value, identifier_patterns finds ids in a message. Neither replaces the other.

Mistakes a beginner makes:

  • A raw string, or a single pattern, instead of a list of re.compile(...). The workflow fails to load with "identifier_patterns holds '...'; write re.compile('...')" or "identifier_patterns must be a list of compiled patterns (re.compile)". A pattern that does not compile fails the load too.
  • Copying a field's anchored pattern (^...$) into identifier_patterns. It is searched inside the message, so an anchored pattern finds nothing unless the message is the id alone. The load reports it ("identifier_patterns are searched inside the message; remove the ^ and $ anchors"). Use \b instead; a pattern compiled with re.MULTILINE is left alone. The reverse also holds: a field's pattern should be anchored.
  • Expecting "4421" to become acct_4421 on a field that is not marked. The widening is decided by the mark, never by the pattern: with no mark nothing is widened, and "4421" stands (or the pattern refuses it). On a marked field that also has a pattern, the value is widened first and then checked against the pattern, on every path.

See also splitting a request for the rest of _commands/_workflow.py.
