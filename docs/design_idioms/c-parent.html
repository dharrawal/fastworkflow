03

The enclosing record

In fastWorkflow the workflow always stands on one object of your application, called the current record (workflow.record). Each kind of record has a context: a folder under _commands/ named after its class, holding the commands for it (see a folder for one kind of object). Most records live inside a bigger one: a user is in a chat room, a todo item is in a todo list. That bigger object is the enclosing record.

Reach for this idiom when a user standing on the inner object should still be able to use the outer object's commands. Standing on the user alice, the person should be able to say "list the users" without first stepping back out to the room. You make that possible with one method, get_parent, that answers "which object contains this one?", and one declaration, parents, that says which contexts that object can be.

It lives in the context's own file, _commands/<Context>/_<Context>.py, in a class that must be called Context; a _<Context>.py with no class Context stops the workflow when it loads. The framework calls Context.get_parent(record) with the live object the workflow stands on and expects the enclosing object back. Read it off the object itself, usually an attribute your application already keeps.

Beside it, in the same class, write parents = ["ChatRoom"]: every context a record of this context can sit in, that is, the contexts whose records get_parent returns. It is a list of context names written as string literals, read as written when the workflow loads, without importing the file. When records nest, the context names itself: a todo list sits in another todo list or in the manager, so TodoList declares parents = ["TodoList", "TodoListManager"]. The two go together, and the load checks it: a get_parent with no parents, or parents with no get_parent, stops the workflow (get_parent is written but no parents is declared: list every context a record of this context can sit in, parents = ["<Context>", ...] ...), and so does a name that is no context (with the name it probably meant), a name given twice, or parents on a context declared occupiable = False. A context with neither is a top-level context, enclosed only by the global commands; omitting parents is the only way to say so. The context of the root object needs neither: it is the root, whatever its context. A get_parent inherited from a Python base class counts, but parents itself is written in the body of class Context.

What the framework does with it at run time:

  • A request the current context cannot serve climbs. The framework looks for the command on the current record's context, then on its enclosing record's context, then that record's enclosing record, up to the root object set by the startup command (see the root object). The global commands are reachable too (see commands with no object). A command typed by its exact name is found on the nearest record that has it.
  • The command runs on the record it was found on. If "list the users" is found on the ChatRoom, then inside that command workflow.record is the ChatRoom. The workflow itself stays on alice, so the next request starts from alice again. A direct action from a client (an MCP tool call or a direct HTTP action) climbs the same way: it runs the command on the nearest record of the chain whose context has it. The command's Input validators read that record too, on every path: a "/" message, a direct action, a part of an agent-mode turn (its draft, its missing-value question and reply, the review's re-draft after an edit, and the run's check).
  • "Go up" moves one step out. The built-in go_up command sets the workflow on the enclosing record that get_parent returns.
  • What get_parent returns is checked against parents. A record whose context is neither a declared parent nor a context that inherits one (a PremiumUser is a User) stops the climb with MissingGetParentError, naming the context, its declared parents and the record returned, for example "the get_parent of context Book returned a Member record, but Book declares parents = ['Library'] in _commands/Book/_Book.py: a Book record sits only in those contexts (or one that inherits one). Return the enclosing record, or add 'Member' to parents". return None is always allowed.

The climb follows the live objects, not the class names. A todo list nested inside another todo list climbs to that outer list, and only the top list climbs to the manager, with the same get_parent for both. One reader still compares class names: the one that builds the route plans of navigation names each class once, so from a nested list its plan to the manager has one go_up where two are needed, and after it the agent stands on the outer list. Requests and go_up are not affected. The climb stops at the root object. The root has no enclosing record, and the framework never calls get_parent on it, so the root's Context class needs no get_parent at all: leave it out. Write get_parent only for records that sit inside another record.

Three mistakes a beginner makes:

  • A get_parent that returns None for an object that is not the root. The climb jumps from the user straight to the global commands, and the ChatRoom's commands are not offered while the workflow stands on a user. return None is the explicit way to say "go straight to the global commands", so nothing is logged; write it only when that is what you mean.
  • No _User.py, or a Context class without get_parent, for a record that is not the root (for example a class written only for a display name). Such a context declares no parents, so a command that enters it with @descends_to from another context already fails its load (see move onto a record). In a workflow with a root object both are one error at run time too: the first climb from that record raises MissingGetParentError, naming the context, the file to write and the method to add, whatever climbs: the lookup of a request or of a typed name, a direct action, the route plans of navigation, go_up. Nothing catches it. A command that moves the workflow onto such a record fails at once, and the workflow stays where it was. In a workflow with no root, no file and no get_parent mean the same as return None: the climb goes straight to the global commands.
  • Counting on a base to supply it. A context that gets commands from a base (see commands shared through a base) does not get the base's get_parent. PremiumUser below needs its own _PremiumUser.py, with its own get_parent and parents; without it, the first climb from a premium user is the error above.

The framework passes the record positionally; name the parameter record. The old name command_context_object fails the workflow load.

The whole picture is generated. fastworkflow command preview <workflow> writes the workflow's object model, drawn from every context's inherits, parents and occupiable and every command's @descends_to, to _object_models/<workflow>.md beside the planning command previews, and --check fails when it is stale. Nobody writes it by hand. No file declares the root: it is the record the workflow sets as workflow.root at run time.

See also move onto a record, which is how the workflow comes to stand on the inner object, and a record's name and identity, which lives in the same Context class.
