A plan in place of a body

A planning command is a command whose job is to run other commands of your workflow, in a fixed order. It is written like any command file, with the same Signature. The difference is the second class. An execution command has a ResponseGenerator, whose code does the work. A planning command has a PlanGenerator instead, whose methods return the steps. Those steps become a numbered plan, and the framework's own code runs every step it can.

Reach for one when a family of requests is always answered by the same few commands you already have, in the same order: find, then open, then read, then answer. Writing the order down means the agent (the language model that carries out a turn) does not have to find it each time, and does not get it wrong. A planning command adds no new ability to your workflow: every step runs an existing command. If one call into your application could do the whole job, write an execution command instead. It is shorter, and it also runs in assistant mode (fastworkflow run --assistant) and through direct API and MCP calls, which refuse a planning command.

This is the library example's count_books. It runs find_book, an execution command of the same folder, and writes the answer from what that command returned.

What the framework reads, part by part:

  • The file's place. It sits in _commands/Library/, so it belongs to the Library context and its name is Library/count_books, exactly as for an execution command.
  • Signature is the same as an execution command's. The docstring is the description that lists and matches the command (the purpose sentence), plain_utterances are example requests that train intent detection (seeds), and Input holds the values taken from the request (an input). A planning command's field types are narrower than an execution command's, because its values arrive as text; the list, and the message for Optional[int], are on field options. A str value stands as the model filled it, after the template-token, pronoun and vocabulary-word screens (a value the request names as a record passes them, and a pronoun becomes that record when the request names exactly one, with a note on the call); the example carries copied_from_command_text because the query must be words the user wrote, and only a marked field is held to them, by the same check and with the same sentences to the extraction model as on an execution command (the request's own words): an unmarked field is not told to copy the request, nor compared with another field.
  • PlanGenerator is the switch. Its presence makes the file a planning command. A file that defines both ResponseGenerator and PlanGenerator does not load. Like every other mistake below, it skips only that one command (see what a mistake stops).
  • Each public method is a phase, run in the order written, and returns its steps as a list. find is the only phase here. run("find_book", query=...) writes a step that code runs itself (a step the code runs). The return annotation -> FindBook.Output hands on what find_book returned, and a later method receives it as the parameter find (what a phase hands on). The methods only build steps; they must never call your application or read its data. Nothing enforces that: the framework calls every phase method when the files load, once for each combination of placeholder inputs, and again when the plan runs and when a paused plan resumes. So a phase must depend only on its input: one that fails on the placeholders is a load error, and one that calls your application would do so at load time.
  • __result__ runs after the last phase and writes the answer in plain code (the answer, in code). Without it, the agent writes the answer; with no agent model the run ends at an answer stop with a statement of what ran, written by code.

Two beginner mistakes, both caught when the files load (run fastworkflow command run-code or fastworkflow command preview --check to see them before you start the workflow). A step that names a command that does not exist, such as run("find_bok", ...), is reported as a step runs 'find_bok', which is not a command of the workflow, and the planning command is skipped. A phase annotated -> FindBook.Output whose steps never run find_book is reported as phase 'find' hands on find_book's Output, but none of its steps runs find_book.

Where a planning command runs depends on the entry point. In assistant mode (a "/" message, or --assistant) it runs when it resolves to the command and code can do every step: no prose or conditional step, no classifier_confirms or classifier_decides field, no phase decided at run time, and a __result__; otherwise the reply says ... is a planning command; it runs in agent mode with the reasons. With no agent model configured nothing is refused and the plan runs up to its first open step. Direct API and MCP calls refuse every planning command, even a mechanical one.
