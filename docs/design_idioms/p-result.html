The answer, in code

A planning command (a command whose PlanGenerator lists steps that run other commands; see a plan in place of a body) ends by answering the user. __result__ is the method of PlanGenerator where you write that answer yourself, in plain Python, from what the steps found. Reach for it whenever the answer can be built from the facts: it costs no model call, so the same facts always give the same words.

The framework calls __result__ once, after the last phase (a phase is one method of PlanGenerator that returns steps). It passes arguments by parameter name:

  • input is the command's Signature.Input, with the values of this call.
  • Any other parameter must be named after a phase. It receives that phase's facts, usually the Output of the command the phase ran (see what a phase hands on), as a Pydantic object you read with dots. A phase that ran once per item (see once per item) arrives as a list of them.
  • A phase that was skipped (it returned []; see a phase that does not run) arrives as None; so does an optional phase that failed. A phase that ran once per item over zero items arrives as an empty list, not None. Test for it first. A default on the parameter changes nothing: the framework passes None for any phase that did not run.

This is the whole command from the library example. The find phase runs find_book; __result__ turns its total into a sentence.

Run with query "Austen", fastworkflow command run-code on a copy of the example prints answer written by __result__: and, on the next line, indented, Austen matches 2 books. (count, from fastworkflow.planning, writes "1 book" or "2 books".)

What you may return, and what each leads to (only the value counts, except that a return annotation of str or another model on a command that declares an Output is refused when the workflow loads):

  • A non-empty str (only when the command declares no Output): that text is the answer, exactly. No model is asked to write or reword it.
  • A Signature.Output (only when the command declares one, and exactly that class): the answer text is the Output as JSON, and the object rides along for a client or for a planning command that called this one. See what it returns.
  • A fastworkflow.CommandResponse(response=..., output=...): your sentence is the answer, and the Output rides along. Use it when the command declares an Output and a person should read a sentence, as in the second example below.
  • fastworkflow.planning.ANSWER_BY_MODEL: the one way to leave the answer to a model, written on purpose, for a command that declares no Output (one that declares an Output and returns it fails the call: the Output is its answer). A model writes the answer from the facts, exactly as when there is no __result__; the constant lets one branch leave the answer to a model while another writes it. If no agent model is set (LLM_AGENT unset), there is no model to write it: the command does not fail, it ends as a stop. The answer text then states, in code, which steps ran, each step's own result and the facts recorded, then says that the wording needs a model; the same stop comes back as data in the fw_not_run artifact.
  • Anything else, including None (a branch that forgot its return gives None), an empty string, a number, an object of another class, or a str when the command declares an Output, or an exception raised inside __result__: the command fails, as it does when an execution command's __call__ goes wrong. For None the message reads "__result__ returned None; it must return the answer, or fastworkflow.planning.ANSWER_BY_MODEL to leave the answer to a model". The user is told which command failed and why, and no model writes an answer in its place, so a bug in __result__ cannot hide behind a fluent sentence. raise fastworkflow.Refused("...") is the way to decline on purpose: it fails the command with your message. A command with no __result__ at all still leaves the answer to a model.

The framework may add a short note after your text, for example that a phase reading many items stopped at its cap. With no agent model set, the answer also ends with a line naming the command that ran, such as "(Ran Library/count_books.)". These notes are added to the answer text only, not to the command output's response. __result__ itself makes no model call, but a plan with a step the code cannot run still runs the agent for that step.

Run on a copy of the example, "Dune" answers "Dune is by Frank Herbert; the library owns 3 copies." and "Nope" skips the book phase and answers "No book matches Nope.". Both carry the command's Output. To see the answer without running anything, fastworkflow command preview prints a line "Written by `__result__`:" with each fact shown as a placeholder, judged by the run's own rule: the command's Output is shown as the answer as JSON written by code, a text or a CommandResponse as the answer text, ANSWER_BY_MODEL as an answer a model writes, and every return the run refuses (another model class, a text when the command declares an Output, ANSWER_BY_MODEL when it declares one, None, an empty text or any other type) as a failed call with the run's message. fastworkflow command run-code prints "returned ANSWER_BY_MODEL, so a model writes it" and treats None as a run error (exit 1).

Beginner mistakes, each caught when the workflow loads (the command is skipped and the error names the file):

  • A parameter that is not input or a phase name, for example found for a phase called find: "__result__ takes 'found', which is not a phase of this command".
  • Declaring Signature.Output with no __result__: "Signature.Output is declared, but nothing builds it; return it from __result__(self, input, ...)".
  • Writing the answer as a last phase of "say that ..." steps: "writes the answer as 'say that' lines, which code no longer copies; return the text from __result__(self, input, ...) instead".
