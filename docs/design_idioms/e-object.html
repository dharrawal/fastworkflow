The record it acts on

A command's code almost always needs one object of your application to work on: the library, this book, this member. Read it from workflow.record. Assign it when the user should pick one object ("open book b1") and then talk about it without naming it again ("who wrote it?"). One attribute does both jobs: reading it gives the object the command acts on, and assigning it moves the user onto another one.

Some words first. A record is a live object of your application, an instance of one of your own classes, such as Library, Book or Member. Its context is its class name, and the folder _commands/Member/ holds the commands that act on a Member (see a folder for one kind of object). The workflow stands on one record at a time, the current context. It starts on the root record that the startup command builds (see the root object) and moves only when a command moves it.

Read it

The framework calls your ResponseGenerator.__call__ with workflow, the live workflow, as its first argument. workflow.record returns the record this command was invoked on. In show_member below that is the member the workflow stands on. The type annotation member: Member is only for you and your editor; the framework does not read it. Reading workflow.record never moves anything. Read outside any command (in a test or a harness), it is the record the workflow stands on.

Where a request is looked up

The record is not always the one the workflow stands on. A request is looked up along a path, nearest first: the current context's own commands, then those of any base it shares commands through (see commands shared through a base), then those of each enclosing record, one level up at a time to the root (see the enclosing record), then the global commands, the files directly in _commands/ (see commands with no object). That is the order for a name typed exactly. For plain words in a workflow with a trained global model, the global scope is asked first and a confident answer there runs before the nearer scopes are asked. A command found this way runs on the record where it was found. A command reached by its name with no lookup (an MCP tool call, a direct HTTP action, a step of fastworkflow command run-code, an approved call run after its yes) runs on the same record: that of the nearest scope on this path that has it, the root for a global command; the workflow does not move.

So in the library workflow, standing on the member Ann Lee, the request "how many loans are overdue" finds no such command in Member. The framework climbs to her library, finds count_overdue in _commands/Library/, and runs it with workflow.record set to the Library. The workflow still stands on Ann Lee afterwards, so her commands stay one request away. The same rule gives the other cases: a command shared through a base, such as _commands/Record/add_note.py, gets the Book or Member it was invoked on, never a plain Record, and a global command gets the root record. workflow.is_record_root tells you whether workflow.record is the root.

Move onto a record

open_book moves the workflow from the library onto one book, in three parts:

  • library = workflow.record reads the record the command was invoked on, the library, into a local.
  • workflow.record = book is the move. From now on the workflow stands on the book, and the next request is looked up along the path above starting at Book: Book, then its base Record, then Library, then the global commands. So show_book runs on the book, and find_book still runs on the library.
  • @fastworkflow.descends_to("Book") on the ResponseGenerator class tells the framework, before anything runs, that this command is the way into Book. A name that is no context of the workflow, such as "Bok", fails the load of the command: @descends_to("Bok") names no context of the workflow; did you mean "Book"? The framework reads it to plan routes: when a request needs a Book command while the workflow stands on the library, the agent is told to run open_book with a book_uid first. Its required input book_uid is the value that route needs (see a handle's producer).

The user leaves the book with the built-in go_up or reset_context.

@descends_to always declares an unconditional move: the plans and the agent assume the command enters Book whenever it runs. A command that moves only sometimes still declares it, and assigns workflow.record only on the runs that move; give such a command a required input, because a plan's code runs a mover with no required input unasked on its way into the context, and a run that does not move leaves the plan's next step looked up from the wrong record. A context that no object ever is, such as a base that only shares commands, is not a place to move to: its class says occupiable = False (see commands shared through a base), and a @descends_to that names it fails the load of the command. A command that always moves into a context other than its own and takes no required input does nothing but move, so the framework never offers it to the remote model as the answer to a request; the local model and its exact name still reach it. open_book needs book_uid, so it is matched like any other command.

Beginner mistakes

  • Reading workflow.record again after assigning it. It still gives the library, not the book: until your command returns, the getter keeps the record the command was invoked on. Keep the book in a local.
  • Assigning workflow.record without @descends_to. A command may move the session only onto a context it declares: the command fails with "open_book moved the workflow onto a Book record but declares no @descends_to ... Declare @descends_to("Book") on its ResponseGenerator. The move was undone", and the workflow stays where it was. When @descends_to names another context, the failure names the declared one ("... but declares @descends_to("Member"), and Book is not Member nor a context that inherits from it"). "Onto the declared context" means the record's context is the declared one or one that inherits from it in context_inheritance_model.json: @descends_to("User") covers a PremiumUser. A move onto another record of the command's own context (one work item to the next) is a move too, and is declared the same way. Setting workflow.root in the startup command is not a move (see the root object), and a command that declares a move and, on this run, does not make it has not moved.
  • Assigning workflow.record and then raising, Refused included. The framework puts the workflow back on the record it stood on before the command, so the user sees a failed command and has not moved (an ask_user question keeps the move, since the command resumes where it stood). Still assign last, after every check, as open_book does.
  • Assigning a record whose class is no context of the workflow (a typo in the class, or a folder named apart from the class). The command fails with "open_shelf moved the workflow onto a Shelf record, but Shelf is no context of the workflow: a context is the folder _commands/Shelf/ ...", and the record is put back. In a workflow with a root, a move onto a record other than the root whose context has no get_parent fails the same way (see the enclosing record).
  • Treating workflow.record as "where the user is". In count_overdue run from a member it is the library, not the member. Put a command in the folder of the record it needs, and that is the record it gets.
  • Using the old names workflow.current_command_context or workflow.command_context_for_response_generation. Both are gone: reading or assigning either raises AttributeError naming workflow.record as the replacement.
