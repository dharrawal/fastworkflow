An input

An input is the list of values a command needs before it can run. You write it as a Pydantic model named Input inside the command's Signature class (see one file, two classes). Each field is one value. Reach for it whenever a command needs something from the user, such as a name to search for or a page to start at. A command that needs nothing has no fields.

When a user types "find the book Dune", the framework has to turn that sentence into query="Dune". That step is called parameter extraction. You never write it: the framework reads your Input and does it in this order.

  • Fill. A language model (the one named by LLM_PARAM_EXTRACTION in fastworkflow.env) reads the request together with each field's name, type, description, pattern and default, and proposes a value for each field. Everything it is told about a field comes from these declarations, the same on both kinds of command: "Copy it exactly as the request writes it" only for a str you marked (below; a marked int is told "A number the request writes." and a marked list[str] to copy each item), "True only when the request asks for it" for every bool ("False only when the request asks against it" for one that defaults to true), and the pattern.
  • Check. Code refuses a value that is plainly not a value, such as a placeholder, and checks a field you marked against the request (the strict check, below).
  • Validate. The field's pattern is checked (the whole value must match), then pydantic checks the types and the other constraints, such as min_length. Then your own validators run (see correct or refuse).
  • Retry once. If a check or a validator refused a value the model proposed, the model reads the request one more time with the reason attached; so it does when none of its answers could be read into the fields' types. The second answer changes only the fields the first one left open (refused, reset or missing); every other field keeps its first value, and the checks' own corrections are kept. If a refusal names no field, or the first answer could not be read at all, the second answer is taken whole. A value that is simply missing gets no retry.
  • Ask. Whatever is still missing or refused is asked for in one question.

What each thing you write is used for:

You writeThe framework
the field nameshows it to the user in questions, with underscores as spaces (book_uid becomes "book uid"). Pick a name a user would understand.
descriptiongives it to the extraction model as the instruction for that field. Say what the value is and where it comes from. With no description the model only sees "The query".
examplesdoes not show them to the extraction model (a model copies what it is shown). The framework builds sample requests from them for the extraction model, though those samples do not reach its prompt (a known defect); they also feed the "for example" in a question after a wrong format, and the schema clients see.
no default (query: str = Field(...))treats the field as required. If the request does not give it, the user is asked. Do not write default="NOT_FOUND": that is the framework's own marker for a value nobody gave, and declaring it as a default is a load error of the command.
a default, or Optional[...] = Noneuses the default when the request leaves the value out. It never asks for it. Optional[int] and int | None mean the same thing everywhere. A planning command's input is narrower than an execution command's, because its values arrive as text; the list of types is on field options.
Literal["book", "member"]accepts only those values. The model sees them as the allowed choices. A value outside them is refused for that field only (the user is asked about it, with the allowed values; the other fields keep theirs), and a member in another case or spacing takes its declared spelling.
pattern=r"..."tells the model the format ("Must match the pattern ...") and refuses a value that does not match the whole pattern, on every path (the "/" path, the plan review's draft and a typed planning call alike), after a marked id has been widened to the id the request writes. A compiled pattern keeps its flags. The question names the field, the value, the pattern and your first example, so give one. A pattern only validates: it has no effect on the strict check below.
json_schema_extra={...}turns on one extra behaviour per key. Every key is listed on field options, and any other key fails the load (write examples, description, default, title and deprecated as Field() arguments: a planning command refuses them here, and an execution command's Input accepts them here only as JSON Schema annotations); from_command_output has its own page, a handle's producer. The one below is taught here.

An Input may subclass another model of yours (class Input(TitleInput), the base in a _ helper module): the inherited fields are extracted, asked for and checked like fields written in place (see shared phases).

The model's value is used. By default, whatever the model proposes for a str or int field is kept: it may convert the request (a date written "tomorrow" becomes 2026-11-22), so the framework does not compare it with the request.

Checks that always run, whatever you write. A few things can still refuse, change or clear a value you did not mark; no option turns them on or off. (1) Code refuses, on every str field, a value that is entirely one template token (a variable name in braces or brackets: {name}, <name>, <ID>), a value of only punctuation, and a value the request does not write that only repeats the field's own name (uid for a book_uid field). It also removes quotes around a whole value (unless the request itself writes them), turns a made-up number (such as 2147483647, or anything above 253) into the field's default (refused when there is none), refuses a negative number in a field with no ge or gt whose name holds one of the words start, skip, offset, limit, count, page or size (declare ge to say what a number field accepts), and, on an execution command, treats a value that is a command's name in identifier form (find_book, Library/find_book) as not given. Nothing else is judged by its look: "Adam Smith" and "John Doe" are values, so is an id such as SKU_42, so is a<b, so is a JSON string such as {"a": 1} (kept as written), and <Dune> is the value Dune in brackets (mixed case, a digit or a space makes it a value; <dune>, in one case, is a placeholder). (2) Code treats a free-text value that is only a pronoun, or only a word of your workflow's own vocabulary (the kind of record it handles, for example "book" in a library), as missing, and the question says why. On a planning command a value the request names as a record (a name it writes) is never screened, and a pronoun becomes that record when the request names exactly one, with a note on the call. A description that lists words ("One of: book, member") exempts none of them: a fixed set of values is a Literal, which is never screened. (3) When JEV_API_KEY is set, the remote decision model is asked once per filled field you did NOT mark whether the request gives the field a value at all, and a field it is at least 90 percent sure is not given is reset to its not-given value (asked for when required); FW_JEV_FIELD_GIVEN=off turns this one off. Measured on recorded extractions, such a reset removed an invented value 266 times in 267. A marked field is not asked about: the strict check decides it.

The strict check. To require the user's own words, mark the field json_schema_extra={"copied_from_command_text": True}. A marked str must be written in the request, or it is refused, whether the field is required or optional (a marked value the model did not give is not checked); the test is that the value appears in the request as whole words (its first and last characters do not continue into a letter or digit of the request, so "dun" is not written in "dune"), case is ignored, any kind of dash counts as a plain dash, and a kept value takes the spelling the request uses. An id the model cut short inside an id the request writes is widened to the whole id (identifier formats). Two marked fields may hold the same value only when the user's request writes it as often ("stores in New York, New York" fills a city and a state). Otherwise an optional one is left empty, with a line on the review and on any question that says which field and why ("state left empty: 'Albany' is written once in your request and is the city."), and the command runs without it; when both are required, one of them is refused and asked again. Fields you did not mark are never compared with each other. A marked int must be a number the request writes, in digits or as number words (zero to twenty, a tens word alone such as "thirty", and tens followed by a unit such as "twenty five"); a decimal such as 3.5 and a stretch like "one hundred" are not read as a whole number. For find_book (the first example below):

  • "find books by austen" and the model says Austen: kept, as austen.
  • The model says Middlemarch, which the request does not contain: refused.
  • A marked int: "find dune from row 10" with start=20 is refused, and so is any number when the request writes no number at all.

Mark a field when the user must have written the value: a name, a title, an id. Leave it unmarked when your code converts it. A value the model did not give (the default, or nothing) is never checked. A Literal, a bool or a value from an allowed list cannot be marked: the load refuses the mark, because the type already limits the value. Only a str, an int or a list[str] takes it, so a float, a date or a list[int] cannot be marked either. On a planning command any Optional[int], marked or not, fails that command's load: give the int a default (start: int = 0). On an execution command a marked Optional[int] = None loads: an absent value is not checked and a given one is. To see which unmarked fields might need it, read the argument_check_not_in_request attribute on the extraction span: it names the fields whose value the request did not write.

The question. When a required value is missing, the user sees a question built from your field names, such as "I can't run find book yet: your request does not give the query. Which query should I use?" Several open values are asked in one question, and the user replies with name: value lines or with the values in order separated by commas. The question repeats while each reply fills or fixes a value. After two replies in a row that make no progress, or a reply of cancel, it stops asking, and the command does not run with that value missing. In agent mode the question goes to the agent instead of a person.

A bare value for an agent. An agent often calls a command as find_book Dune. In agent mode the framework reads the agent's own text in code, with no model call, in four forms tried in order: <query>Dune</query>, query=Dune, the command name followed by one value, and the command name alone; any other text goes to the model. The one value goes to the field marked json_schema_extra={"command_text_after_command_name": True}, which takes the whole rest of the text, or, with no mark, to the class's only str field, and then only a single word (find_book Ann Lee goes to the model). A first word that names the target field (find_book query Dune), or the last part of its name (open_book uid b3), is dropped. Mark at most one str field, on an execution command; two marks fail the load. Do not mark a free-text field of a command that changes data, because prose sent by mistake would become the value.

How the question form draws a field. The chat page asks for missing values with a small form. By default a str gets a one-line box, and a Literal gets radio buttons when it has five values or fewer, and a drop-down when it has more. The one display hint an Input field takes is json_schema_extra={"ui": {"widget": "textarea"}}, which gives a str a multi-line box for long text, or {"widget": "radio"}, which forces radio buttons on a Literal of any length. Nothing else reads it: no check or extraction changes, and a client other than the chat page may ignore it. The load refuses textarea on anything but a str, radio on anything but a Literal, any other widget name, and any output hint (such as hidden) on an Input field; the command then does not load. The hints for an Output are on how a result is shown.

Two beginner mistakes. First, a str field whose value the user never writes as such, like a date written "tomorrow" that your code needs as 2026-11-22. If you marked it copied_from_command_text, the strict check refuses it and the user is asked again and again: leave it unmarked (see the request's own words). Second, giving a field a default when the command cannot do anything sensible without it. The user is then never asked, and the command runs with the default.
