A handle's producer

Some inputs are handles: an id, a uid or a code that the user cannot make up and the model cannot guess. A command that takes one can only run after some other command has handed the handle out. from_command_output is how you write down which command that is. Reach for it on every Input field that holds a handle.

In the shipped library example, open_book needs a book_uid such as b3. Nobody knows that uid by heart; find_book searches the catalogue and returns the uids it found. So open_book's field says it comes from find_book.

A command is a Python file under _commands/ with a Signature class. Its Input is a Pydantic model of what the command takes, and its Output a model of what it returns (see an input and what it returns). The producer declaration is one key in the field's json_schema_extra. Its value is "<command>.<field>": the producer command's name, a dot, and the name of a field of that command's Output.

The producer's side needs nothing special, but its Output field must exist under that name, and its description should say what the handle opens. The types must fit: the consumer's str may come from a producer's str or from one item of a list[str], as here.

When the workflow loads, the framework checks each declaration and turns it into an edge from the producer to the consumer. At run time that edge does six things for you:

  • The agent's planner reads a list of the commands. Beside book_uid that list shows available_from: ['Library/find_book.book_uids'], and the planner is told to follow these edges, so it calls find_book first and then open_book.
  • When one request holds both steps ("find Dune and open it"), the second part takes book_uid from the first part's book_uids (the one uid itself when exactly one book was found). It is never asked for. When several books were found the value is the whole list as JSON text, which open_book's pattern refuses (a field with no pattern takes that text as its value): the user is not asked which row. When the earlier part's answer is not JSON, its whole answer text becomes the value.
  • When open_book is called with no uid, the question to the user of an execution command adds the line "abort and use the find_book command(s) to get book_uid information." That line appears only when the value is missing, and a planning command's missing-value question does not name the producer, so still write a good description.
  • When the agent's listing is narrowed to the commands a request needs, the producers of those commands are added to it, so the agent can run find_book before open_book.
  • In a planning command, a run("open_book") step that leaves book_uid out takes it from the only row the command run just before it listed (see a step the code runs).
  • run("open_book", named=...) opens a row by the field that declares a producer: with exactly one such field it is that one, otherwise the one required field named like an id (..._uid, ..._id) (see the row a listing named). A second declared field therefore changes which field named= uses.

Always name the field: a bare command name such as "find_book" is an error (see below). A list of these strings names several producers, for a handle that more than one command hands out. A producer in another context is written "Context/command.field", such as "Library/find_book.book_uids". Without the Context/ part the name must be found exactly once in the consumer's own context, the contexts it inherits from, or the global commands (a context is the kind of record a command acts on; see a folder for one kind of object).

Name a producer the user can actually reach from where the consumer runs. A command in a sibling context is not reachable, and an edge to it sends the planner down a dead end. The load does not check this for a qualified name such as "Library/find_book.book_uids": it only checks that the command and field exist and fit. An unqualified name found only in contexts off the consumer's lookup path fails the load with a message that says so and asks you to write the qualified name only when a user can be in that context before running the command; if you do, confirm by hand that it is reachable. (An unqualified name found more than once on the path fails with "qualify it", which is safe.)

Three beginner mistakes, and what you see:

  • A declaration that does not resolve: a misspelled field such as "find_book.uids", a command that does not exist, a field of a type that does not fit, or a field of the producer's Input (find_book.query: "find_book's query is an Input field; from_command_output names the Output field a value comes from"). The command that wrote it does not load. fastworkflow run_cli, fastworkflow train and the server print it as a problem before they start, with the file, the field and the reason: Library/open_book: .../open_book.py: Input.book_uid (from 'find_book.uids'): Library/find_book has no Output field 'uids'. The rest of the workflow loads, and fastworkflow command preview <workflow_folder> --check reports the same error and exits 1.
  • Writing only the command, "find_book", with no field. That fails the load in the same way, and the message lists the fields of find_book's Output that fit: a bare command name is not accepted; write "<command>.<field>", an Output field of find_book that fits str: find_book.book_uids, find_book.titles. If the producer returns one block of text with no field that holds the handle, leave the declaration out and describe the handle in the field's description.
  • Writing available_from yourself, or putting from_command_output on an Output field. Both are mistakes: the framework writes available_from from your declaration, and only an Input field takes a producer. So does a planning command that names one of the commands its own steps call as a producer (its steps run it anyway; describe the value with description), and a from_command_output on a field of a planning command's facts model. Like an unresolved declaration, each fails the load of the command that wrote it and is listed with the file and the field (see what a mistake stops).
