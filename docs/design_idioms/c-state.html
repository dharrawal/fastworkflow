04

Remember the object

Your workflow stands on a live Python object, such as a Library, in the server's memory, and the server sometimes puts a conversation away and brings it back later. Class methods on the root's context class tell the framework how to save your object as plain JSON and build it again, because it cannot know what is inside it. Write get_state and from_state for every workflow you serve over HTTP or MCP; add get_locator and find_by_locator when a command moves the workflow onto a record inside the root.

Some words first. A record is a live object of your application; its context class is the class Context in _commands/<ClassName>/_<ClassName>.py (see a folder for one kind of object). The root is the record your startup command builds (see the root object). The current record is the one the workflow stands on now. A session is one user's conversation.

When a session is saved and restored. The server (fastworkflow run_fastapi_mcp) keeps at most MAX_LIVE_SESSIONS sessions in memory (50 unless you set it). When one more is opened, it evicts the oldest idle session: it writes a snapshot, a checkpoint, to disk and drops the session from memory. A clean shutdown checkpoints every idle session too. The session's next message, perhaps after a restart, rebuilds it from the checkpoint, with any question still out (say "Which member did you mean?"), so the user's answer still lands. A checkpoint is read back only by the same command files: its folder is keyed on the paths, sizes and modification times of every file under _commands/ (the framework's own included). Any edit there, a fresh checkout, a moved folder or a reinstall of fastworkflow starts every saved conversation over, with no message. The command line (fastworkflow run) keeps its one session in memory and never calls them.

Save and rebuild the root

What each part does:

  • get_state(cls, record) is called when the session is checkpointed. It gets your live object and returns a dict of plain JSON values. The library's to_state_dict writes its branches, books, members and loans as lists of small dicts.
  • from_state(cls, state, workflow, *, state_version) is called when the session comes back. It gets that dict and returns a new object of the same class. workflow is for things you compute rather than save, such as a path under workflow.folderpath.
  • state_version is a number you choose (1 when you leave it out). It is saved next to the dict and handed back to from_state, which reads an older shape or refuses it by raising fastworkflow.UnsupportedStateVersion. Bumping it is an edit under _commands/, which already puts older checkpoints out of reach (above), so the check can fire only when the number itself is read from your application code (for example state_version = Library.SCHEMA_VERSION, imported from your application) and that code changes it with no edit under _commands/. A number written in the context file and left unchanged never refuses: from_state then gets an older-shaped dict with the same number.

The framework saves one object: the root, or the current record when the workflow has no root. It calls the hooks of that object's class only. Save the root whole and once: to_state_dict leaves out each book's back-reference to its library, and from_state_dict builds each book against the new library. The shipped Book and Member classes also carry get_state and from_state; they run only in a workflow with no root, so the example app never calls them.

What goes wrong when a session cannot be saved. A session whose object cannot be saved is pinned: it is never evicted. The conversation itself works, but:

  • The server goes over its session limit and memory grows. Past four times the limit (MAX_LIVE_SESSIONS_HARD), a new conversation gets HTTP 503 unless a pinned session idle for 30 minutes (PINNED_SESSION_IDLE_TTL_SECONDS; 24 hours, PROTECTED_SESSION_IDLE_TTL_SECONDS, when a question waits for its user) can be dropped, losing its object and any open question. The server's periodic reaper also drops such idle pinned sessions whenever the live count is above the limit, not only at four times.
  • A shutdown writes no checkpoint for it, so after a restart the conversation starts over from the startup command.

At startup the server lists every context class with no get_state, except one declared occupiable = False: no object is ever of that class, so it is never the saved object and needs no hook (the library's Record needs only that one line; the shipped file also keeps a get_state returning fastworkflow.EPHEMERAL, which is not needed). The first time a session is pinned the server logs a warning naming the class and the reason. For an object not worth saving, return fastworkflow.EPHEMERAL from get_state: the session is still pinned, on purpose, and nothing warns about it. The hooks come in pairs. A class with from_state but no get_state, or with one of get_locator and find_by_locator without the other, fails the load ("Member: has get_locator but no find_by_locator; the two hooks come as a pair: write both, or neither"), which fastworkflow run, fastworkflow train and the server report at startup. A class whose get_state returns a dict but that has no from_state is never saved, since it could not be rebuilt: the session is pinned, and the warning says "has get_state but no from_state hook, so its saved state could not be restored".

Beginner mistakes, and what you would see:

  • Forgetting the return. None is treated as a bug, not as "do not save": the session is pinned and the warning says to return a dict or fastworkflow.EPHEMERAL.
  • A value that is not plain JSON. A date, a set, one of your own objects, a key that is not a string, or NaN is refused, never turned into a string. So is one list placed under two keys, which would come back as two lists. No checkpoint is written, the session stays in memory, and the log says "Not evicting ... checkpoint write failed" with the bad value's path (such as $.payload.command_contexts.state.when: date is not JSON-native, the path starting at the saved section's envelope). A tuple is refused too: return a list. Convert it in get_state, say a date to an ISO string. A StrEnum or IntEnum value passes and comes back as a plain str or int.
  • A from_state that fails. If it raises or returns another class, the snapshot is set aside, an error is logged, and the conversation starts fresh from the startup command. Its signature is not checked at load, so a from_state without the keyword state_version fails this way at the first restore.

Find the current record again

A command can move the workflow onto a record inside the root, say one member, with workflow.record = child (see move onto a record). Only the root is saved, so the framework must note where that record sits and find it in the rebuilt root. A locator is a short string you choose that points at one record inside the root; two more class methods write and read it.

  • The pair goes on the context class of the root (here Library), next to its get_state, because the locator points into what was saved.
  • get_locator(cls, record) is called when the session is saved and the current record is not the root itself. It must cover every kind of record a command can move onto: the library's open_book and open_member reach books and members, so the string names the kind and the uid.
  • find_by_locator(cls, anchor, locator) gets the rebuilt root as anchor and returns the record the string names in that root. It looks the record up; it never builds one.

What happens at run time. At save time the framework checks the pair: it calls find_by_locator(root, get_locator(record)) on the live root and requires the very same object back (Python's is, not ==). On restore it rebuilds the root with from_state and calls find_by_locator to put the workflow back on member m2. The user carries on there, and climbing to the library (see the enclosing record) reaches the restored root.

When you do not need the pair. When no command assigns workflow.record, the framework saves "on the root" by itself. With no root, the current record is the object saved, through its own get_state and from_state.

What the user sees without it. If the root has get_state but no locator pair, a session standing on a member is pinned (see above); one standing on the root is saved normally, as long as the record the last command ran on (the response slot, a second saved position) is also the root or can be located; a session whose last command ran on another record, for example one found by climbing, needs the locator pair too, and the log message then says "the response context is not the anchor". When the pinned session is dropped or the server restarts, the user starts over from the startup command, on the root, and any open question is lost. The log warns once per class that "Library has no get_locator/find_by_locator pair to point into it".

Beginner mistakes:

  • Building a record instead of finding it. A find_by_locator that returns Member(...), a copy, or the wrong record fails the save-time check: the session is pinned and the log says "Library.find_by_locator did not round-trip the current context locator 'member:m2'". So does a method that raises, or a get_locator that meets a kind of record it does not handle.
  • Putting the pair on the child's class. The framework reads it only from the root's class, so the session is pinned with the "no get_locator/find_by_locator pair" warning.

Write the hooks once for many classes

When several context classes need the same hooks, do not copy them into each file. Write them once on a plain class in a helper module of the workflow's helper package, such as _commands/_shared/checkpoint.py. The framework never reads that package, so it is neither a command nor a context. Each context class then inherits from it, and a class that needs something different writes that one method itself.

  • The import. From a callback file, write from .._shared.checkpoint import CheckpointHooks: two dots go from _commands/Book/ up to _commands/, then into _shared, the same way a callback file reaches your application code with from ...application.library import Book.
  • What may be inherited. The framework reads each member from the class itself, so get_state, from_state, state_version, get_locator, find_by_locator, get_parent, get_displayname, instance_label_attr and occupiable may all come from a base class. The two declarations may not: inherits and parents are read as written in the body of class Context itself, so one inherited from a base class stops the workflow, and a context that inherits get_parent still writes its own parents.
  • Overriding. A method written in the Context class wins over the inherited one. It can call the inherited one with super().get_state(record) and add to the result.
  • The startup list. A class that inherits get_state is not listed as lacking one; a class that neither writes nor inherits it still is.
