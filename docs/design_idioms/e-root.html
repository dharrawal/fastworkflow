The root object

Most workflows act on one application object, such as the library, and on the records inside it. Before the first request, something must build that object and hand it to the workflow. That is the job of one small global command, startup, which a session runs first. Reach for it whenever your commands live in a context folder (a folder of _commands/ named after a class, see a folder for one kind of object).

The object you hand over is the root object: the record the workflow stands on when a session begins, and the top of every enclosing record chain. You write two things.

  • _commands/startup.py, directly in _commands/, so it is a global command. It has only a ResponseGenerator and no Signature: it takes no input, and a command with no Signature runs only as an action. No name a user types and no words reach it, no listing names it, and training never gives it example requests. That missing Signature, not the name startup, is what keeps it out of routing, listings and training; its name does not matter. Its one line of real work is workflow.root = Library(). Assigning workflow.root also puts the workflow on that object, so the commands in _commands/Library/ can now be found.
  • startup_action.json, in the workflow folder. It is an action: a command called by name, with no language understanding in between. It names the startup command. Each workflow folder needs its own: a workflow that extends another inherits its commands, startup.py included, but not its startup_action.json. Its keys are command_name, command, parameters and workflow_id; any other key (a misspelt params) stops the workflow with a line naming the file and the closest key.

Who runs it. Put the file in the workflow folder and every entry point runs it by itself: the command line, the server and the chat page. Nothing is passed. You pass a flag only to use a different file or to replace it, and then the flag wins over the file in the folder. There are two flags and they differ. --startup_action <file> names an action file, a command called by name with no language understanding; the value may also be the JSON object itself, written inline, starting with {. --startup_command "<text>" gives a message that goes through intent detection like anything a user types, and it suppresses the file in the folder; the command line sends that text as an ordinary message, while the server runs it as a / message. On the server, a session that asks for its own startup action when it is created wins over both flags; a session's own startup_command loses to a process --startup_action. fastworkflow command run-code honours no flag. Only command_name is required in the JSON; command and parameters are optional. A name that is not a command, or names a command that does not load, is a load problem that names startup_action.json and stops the workflow: fastworkflow run exits, the server refuses to start and train stops (see what a mistake stops). fastworkflow build generates _commands/startup.py and a startup_action.json that names it (a startup.py already there is kept unless you pass --overwrite, a startup_action.json always is, and --no-startup writes neither). The command line prints the startup's text before the first prompt. The server runs it when a session is created (/initialize), and the chat page shows it as the session's first turn. fastworkflow command run-code reads the same file. A session saved and resumed gets its root back from the context's saved state, not from running startup again (see remember the object).

Beginner mistakes.

  • Leaving out startup_action.json, or naming it differently. When no flag names a startup either and the workflow has a command with no Signature, nothing could ever run that command: fastworkflow run stops with "startup has no Signature, so it runs only as the workflow's startup action, and nothing names it", and the server logs the same line at startup (a session may still pass its own startup action when it is created; one that passes none stands on no object, where only the global commands can be found). The file must be called exactly startup_action.json and sit directly in the workflow folder.
  • Setting the root twice. workflow.root can be set once per workflow, whatever the object is (an object that counts as false still counts as set); a second assignment raises ValueError: workflow.root can only be set once per Workflow. Build the object in startup only, and move between records with workflow.record (move onto a record).
